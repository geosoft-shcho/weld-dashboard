# weld-dashboard — Cursor 에이전트로 기능을 구현하는 방식

이 문서는 weld-dashboard에서 화면·위젯·기능·버그·연동·리팩터를 만들 때 코딩 에이전트를 **어떤 규칙으로, 어떤 모드 순서로, 무엇을 근거로** 쓰는지 정리한다. **지금 따르는 개선 방식**이 본문이고, 앞부분에 기존 방식과의 차이를 둔다.

- **개발용 코딩 에이전트 하네스(A축)** 이다. 제품 내 LLM 에이전트(B축) 설계 문서가 아니다.
- 도구 중립 요약: 루트 [`AGENTS.md`](../../AGENTS.md)
- 절차 스킬: [`.cursor/skills/work-prompt/SKILL.md`](../../.cursor/skills/work-prompt/SKILL.md)
- 기존(보완 전) 전문: [`docs/2026-11-04/Cursor_에이전트_기능구현_방식_기존.md`](../2026-11-04/Cursor_에이전트_기능구현_방식_기존.md)

---

## 1. 한 줄 요약 (현재)

**코드를 바로 고치지 않는다.** Ask에서 읽고 분석하고, Plan에서 작업 프롬프트를 짜고, 사용자가 확인하면 `docs/<날짜>/<작업>_프롬프트.md`로 저장한 뒤, Agent는 **그 마크다운만** 보고 구현한다. 구현 후 `./scripts/agent_check.sh`와 구현 후 검수를 통과하기 전에는 완료로 치지 않는다. 구현 전에는 앱 목적(`README.md`)과 회사 Flutter 코딩 가이드라인(원격 저장소, 읽기 전용)을 맞춘다.

에이전트는 “알아서 구현하는 AI”가 아니라, **문서로 고정된 작업 지시서의 실행기**다.

---

## 2. 기존 → 개선: 무엇이 달라졌는가

### 2.1 유지한 것 (기존과 동일)

| 항목 | 내용 |
|------|------|
| 모드 순서 | Ask 분석 → Plan 확인 → 프롬프트 md 저장 → Agent 구현 |
| 범위 잠금 | 확인된 프롬프트 밖은 수정하지 않음. 채팅과 파일이 다르면 **파일** |
| 금지 조항 | 「복잡한 코드 제거 및 금지」 매 프롬프트 고정 |
| 제품·코드 기준 | `README` 목적, 원격 guidelines, domain/data/presentation |
| 커밋 원칙 | 사용자 요청 시에만, 목적별 커밋 |
| 트랙 분리 | PRD·document-export·설명은 구현 파이프와 분리 |

### 2.2 개선으로 추가·강화한 것

| 구분 | 기존 | 개선(현재) |
|------|------|------------|
| 흐름 끝 | 구현 → (선택) 커밋 | 구현 → **`agent_check` + 검수** → (선택) 회고 → 커밋 |
| 완료 확인 | UX 등 자유 기입. analyze는 적을 때만 | **`./scripts/agent_check.sh` 기본** + 관련 테스트 + UX |
| 품질 게이트 | “항목에 있으면 본다” | 실패하면 **완료 아님**. 구현 후 검수 체크리스트 |
| 지시 진입점 | Cursor rules/skills만 | 루트 **`AGENTS.md`** (도구 중립) |
| 하네스 인식 | 절차 중심 | **지시/도구/환경/피드백/상태** 층 |
| 학습 루프 | 없음 | 오판·거절 → **회고 → rule/스킬 승격** |
| 커밋 가드 | `.env` 제외 정도 | 기능 구현 직후 **check 통과 전 커밋 금지**, 시크릿 보강 |
| 온보딩 | 방식 md만 | **README → AGENTS.md → 이 문서** |

한 줄: 기존은 **무엇을 고칠지**를 문서로 잠그는 데 강했고, 개선은 그 위에 **돌리고·거르고·남기는(피드백) 층**을 더해 “구현했다 = 끝”을 막는다.

## 3. 하네스 층 (현재)

| 층 | 이 레포에서 |
|----|-------------|
| 지시 | `AGENTS.md`, `.cursor/rules`, `.cursor/skills`, 작업 `*_프롬프트.md` |
| 도구 | Cursor Agent, Shell 등 (요청 범위의 도구만) |
| 환경 | Flutter/Dart, guidelines 임시 클론, `.env` 복사 규칙 |
| 피드백 | `./scripts/agent_check.sh` (`dart analyze`, 선택 `flutter test`) |
| 상태 | Plan 확인, `*_프롬프트.md`, 완료 확인, (선택) 회고 |

---

## 4. 왜 이렇게 쓰는가

| 문제 | 이 방식에서 막는 것 |
|------|---------------------|
| 채팅만 보고 범위가 커짐 | 확인된 프롬프트 파일 밖은 수정하지 않음 |
| 가이드라인·폴더 구조 무시 | 구현 전 원격 guidelines를 워킹 트리 밖에서 읽음 |
| 공정 전용 UI로 고착 | `README` 목적: 범용 멀티모달 가시화 |
| 추상화·헬퍼 남발 | 프롬프트마다 「복잡한 코드 제거 및 금지」 |
| 검증 없이 완료 선언 | `agent_check` + 구현 후 검수 |
| 같은 실수 반복 | 회고 → rule/스킬 승격 |
| 커밋이 섞이거나 자동 커밋 | 요청 시에만, 목적별 커밋. check 미통과 시 커밋 금지 |

## 5. 규칙과 스킬

### 5.1 Always-on Rules (`.cursor/rules/*.mdc`)

| 규칙 | 역할 |
|------|------|
| `work-prompt.mdc` | Ask → Plan → 프롬프트 md → Agent → `agent_check`·검수 |
| `apply-guidelines.mdc` | Flutter/Dart 전 원격 guidelines |
| `dashboard-purpose.mdc` | `README` 목적 확인 |
| `git-commit-push.mdc` | 요청 시에만 목적별 커밋. check·시크릿 가드 |
| `document-export.mdc` | 매뉴얼·발표. 기능 구현과 별 트랙 |

### 5.2 Skills

| 스킬 | 위치 |
|------|------|
| `work-prompt` | 본 절차·템플릿·검수·회고 |
| `apply-guidelines` | 아키텍처·네이밍·폴더 |
| `git-commit-push` | 커밋·푸시 + 검증·시크릿 |
| `document-export` | PPT/PDF 등. 기능 구현에는 쓰지 않음 |

“구현해줘 / 수정해줘 / 추가해줘 / 고쳐줘”면 `work-prompt`를 연다. “프롬프트만”이면 md까지 쓰고 구현하지 않는다.

## 6. 표준 흐름 (현재)

확인된 계획과 프롬프트 마크다운이 없으면 제품 코드(`lib/**` 등)를 고치지 않는다.

```text
사용자 요청 (구현·수정)
        │
        ▼
 Ask — 분석 (읽기만)
        │ Plan 전환
        ▼
 Plan — 작업 프롬프트 + 사용자 확인
        │
        ▼
 Agent — docs/<YYYY-MM-DD>/<작업>_프롬프트.md 저장
        │
        ▼
 Agent — 문서만 구현 (+ guidelines)
        │
        ▼
 ./scripts/agent_check.sh + 구현 후 검수 (+ 선택 회고)
        │
        ▼
 (선택) 사용자 요청 시 커밋·푸시
```

기존 흐름은 여기서 **구현 직후 곧바로 (선택) 커밋**이었다. 현재는 그 사이에 **검증·검수·(선택) 회고**가 있다.

### 6.1 Ask — 분석

- 읽기만. 파일 생성·수정 없음.
- 대상 파일, 현재 동작, 원인, 계약·화면안 확인.
- 프롬프트의 「먼저 읽을 것」「현재 상태」초안.
- 끝나면 Plan 모드 전환을 요청한다.

### 6.2 Plan — 계획

- 작업 프롬프트 전체 작성. 금지 조항 + **완료 확인 기본(agent_check)** 포함.
- 확인 전 구현·프롬프트 파일 작성 금지.
- 해석이 갈리면 가정 금지 → 확인 질문.

### 6.3 마크다운 저장

- 확인한 날 기준 `docs/<YYYY-MM-DD>/<작업이름>_프롬프트.md`
- 채팅과 파일이 다르면 **파일**을 따른다.

### 6.4 Agent — 구현

- 문서에 적힌 파일·동작만 수정.
- 문서 없으면 Plan으로 되돌림.
- 범위 밖 리팩터·이름 정리·스타일 통일 금지.

### 6.5 검증·검수·회고 (개선)

**검증**

```bash
./scripts/agent_check.sh
./scripts/agent_check.sh test/<관련>_test.dart
```

인자 없으면 `dart analyze`. 있으면 analyze 후 해당 `flutter test`.

**구현 후 검수**

- 「바꿀 것」 밖 파일 변경 없음
- 금지 조항 위반 없음
- import·API·proto가 실제와 일치
- `agent_check` 실패면 완료 아님
- 범위 부족 시 프롬프트를 고치고 재구현 (프롬프트만 반복 금지)

**회고 (선택)**

오판·거절한 diff·반복 실수가 있으면 프롬프트 말미 또는 `docs/<날짜>/회고_<작업>.md`에 남기고, 반복이면 rule/스킬로 승격한다.

### 6.6 “프롬프트만”

마크다운까지 만들고 구현·검증은 하지 않는다.

## 7. 작업 프롬프트 구성 (현재 템플릿 요지)

전문은 `work-prompt` 스킬과 같다. 기존과 같고 **완료 확인만 강화**했다.

```markdown
## 완료 확인
- `./scripts/agent_check.sh` 통과 (`dart analyze`)
- 관련 테스트가 있으면 `./scripts/agent_check.sh <test 경로…>` 통과
- <확인할 UX·동작>
```

그 위: 목표, 먼저 읽을 것, 현재 상태, 바꿀 것, 유지할 것, 만들지 않음, 「복잡한 코드 제거 및 금지」 고정 조항.

## 8. 제품·코드 기준

### 8.1 앱 목적

공정에 묶이지 않는 멀티모달 가시화. 시계열·영상·음성·품질을 같은 작업 시각으로. 수집값을 숨기지 않음.

### 8.2 코딩 가이드라인

워킹 트리 밖 임시 클론으로 읽기만. `apply-guidelines` 절차. weld-dashboard에 클론·커밋하지 않음.

### 8.3 계층 (`lib/src/`)

- **domain** — 엔티티, 저장소 인터페이스, 유스케이스
- **data** — 저장소 구현, DTO (`toDomain()`). View/ViewModel에서 import 금지
- **presentation** — View, ViewModel, Coordinator. ViewModel은 유스케이스만

```text
lib/src/presentation/features/<feature>/
  <feature>_screen.dart
  <feature>_view_model.dart
  <feature>_coordinator.dart
```

## 9. 커밋·푸시 (현재)

사용자 요청 시에만.

- 목적별 커밋 (파일 수가 아니라 목적). 목적이 하나면 커밋 하나.
- 기능 구현 직후면 `./scripts/agent_check.sh` 미실행·실패 시 **커밋하지 않음**.
- `.env`·자격 증명·키·시크릿 커밋 금지. 채팅에 시크릿 붙여 넣지 않음.
- 강제 푸시·`--no-verify`·대화형 rebase 금지.

상세: `.cursor/skills/git-commit-push/SKILL.md`

## 13. 체크리스트 (현재)

1. 코드 변경 요청인가? → `work-prompt`
2. Ask에서 대상·현재 상태만 정리했는가?
3. Plan에 목표·바꿀 것·유지·비범위·금지·완료 확인(**기본 검증 포함**)이 있는가?
4. 사용자가 Plan을 확인했는가?
5. `docs/<오늘>/<이름>_프롬프트.md`를 저장했는가?
6. README 목적 + guidelines를 읽었는가?
7. 「바꿀 것」만 건드렸는가?
8. `./scripts/agent_check.sh`(+관련 테스트)와 **구현 후 검수**를 통과했는가?
9. (해당 시) 회고·rule 승격을 남겼는가?
10. 커밋은 요청 시에만, 목적별로, check 통과 후인가?

이 열이 맞으면 현재 레포에서 기대하는 Cursor 에이전트 기능 구현 방식과 같다.
