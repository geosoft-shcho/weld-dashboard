# 파이프라인 실시간 조회 가이드

업무 적재 파이프라인과 **별도로** 적재 흐름(추적)을 쌓고, BE API → FE로 **적당한 실시간** 상태를 보여 주기 위한 정리이다.

기준 파이프라인:

```text
device → http → consumer / AI → DB → BE → FE
```

---

## 1. 목표

한 건의 메시지가 어디까지 왔는지, 각 구간이 몇 ms 걸렸는지  
`request_id` 하나로 FE에서 거의 실시간으로 보이게 한다.

```text
device → http → consumer/AI → (업무 DB)
              ↘
            흐름 추적 (Redis → 나중에 Mongo/DB)
              ↘
            BE API → FE (타임라인·상태 UI)
```

적재 흐름은 업무 테이블과 **따로** 쌓는다.  
FE에 흘려 주는 **조회 API**만 열면 적당한 실시간이 된다.

---

## 2. 단계별 기록 필드

| 단계 | 추가·기록 | 의미 |
|------|-----------|------|
| **device** | `publish_at` | 장비가 메시지를 발행한 시각 |
| **device** | `request_id` | 전 구간 추적 키. 각 미들웨어가 DB(또는 Redis) insert/update 할 때 사용 |
| **http** | `http_received_at` | device 메시지를 수신한 시각 |
| **http** | `http_forwarded_at` | consumer에게 넘긴 시각 |
| **http** | 단계 코드 저장 | `1-b`, `1-c`, `2-a` 등 구간 포인트를 DB/Redis에 저장 |
| **consumer / AI** | `consumer_received_at` | http에게 받은 시각 |
| **consumer / AI** | 업무 DB `created_at` | 실제 적재·추론 결과 저장 시각 |

공통: 모든 기록에 **`request_id`** 를 붙인다.

---

## 3. request_id 라이프사이클 (insert → update)

```text
1) device 발행
   request_id 생성 (UUID 등)
   publish_at 포함해 http로 전송

2) http 수신 직후
   흐름 저장소에 INSERT
   { request_id, status: received, publish_at, http_received_at, ... }

3) http → consumer 전달 시
   같은 request_id로 UPDATE
   { http_forwarded_at, status: forwarded, stages: [1-b, 1-c, 2-a], ... }

4) consumer / AI 수신·처리·업무 DB 적재
   같은 request_id로 UPDATE
   { consumer_received_at, ai_done_at?, db_created_at, status: done | failed }
```

**한 `request_id` = 한 건의 파이프라인 여정.**  
처음에 insert 하고, 다음 단계에서 update 한다.

단계별 히스토리가 더 필요하면 문서 하나에 `events[]`를 append 하는 방식도 가능하다.

---

## 4. Redis를 쓰는 이유 (DB pool)

단계마다 Mongo/SQL에 insert/update 하면:

- 메시지 폭주 시 **커넥션 풀 고갈**
- 추적 쓰기가 업무 적재와 자원을 다툰다

권장:

```text
각 미들웨어
  → Redis에만 기록·갱신
  → 흐름 완료(또는 주기/배치) 때 Mongo/DB에 한 방 저장

BE 실시간 API
  → 우선 Redis 조회
  → 없으면(만료·완료분) Mongo 조회
```

| 저장소 | 역할 |
|--------|------|
| **Redis** | 진행 중 건의 실시간 상태 (FE용 핫 경로) |
| **Mongo/DB** | 완료·실패 이력, 분석·감사 (콜드 경로) |
| **업무 DB** | Asset·시계열 등 본데이터 (흐름 추적과 분리) |

요약: Redis에 기록·기록·기록하고, 마지막에 DB 한 방에 저장한다.  
BE에서는 Redis를 보는 API를 연다.

## 5. Redis 저장 형태 (예시)

키 예: `pipeline:req:{request_id}`

```json
{
  "request_id": "r-9f3a",
  "status": "ai_running",
  "publish_at": "2026-11-13T09:11:00.000Z",
  "http_received_at": "2026-11-13T09:11:00.120Z",
  "http_forwarded_at": "2026-11-13T09:11:00.180Z",
  "consumer_received_at": "2026-11-13T09:11:00.200Z",
  "ai_started_at": "2026-11-13T09:11:00.210Z",
  "db_created_at": null,
  "stages": [
    { "code": "1-b", "at": "2026-11-13T09:11:00.130Z" },
    { "code": "1-c", "at": "2026-11-13T09:11:00.150Z" },
    { "code": "2-a", "at": "2026-11-13T09:11:00.170Z" }
  ]
}
```

- 단계마다 Redis JSON/Hash **update**
- TTL: 진행 중은 정책에 맞게, 완료 후 Mongo 적재되면 삭제 또는 짧은 TTL

완료 시:

```text
Redis 스냅샷 → Mongo insert (이력)
Redis key delete 또는 status=done + 짧은 TTL
```

## 6. AI 추론이 들어가는 위치

AI는 http 직후가 아니라, 주로 **consumer / 외부 도구 구간**이다.

```text
device/FE
  → http
  → queue worker
        ├─ 일반 후처리 (asset-postprocess, audio-extract …)
        └─ AI 추론 (STT · 포즈 · VLM …)
  → 업무 DB + /files
  → API → FE
        └─ (선택) RAG/Ask 등 조회 시점 추론
```

흐름 추적에서는 예:

- `ai_started_at` / `ai_done_at`
- `status`: `ai_running` → `ai_done` | `ai_failed`

## 7. 실시간 조회 (BE → FE)

### BE API (Redis 우선)

예시:

- `GET /pipeline/live?limit=50` — 최근 진행 중 목록
- `GET /pipeline/live/{request_id}` — 한 건 상세·구간 시각
- (선택) SSE / WebSocket — Redis 갱신 시 FE로 push

조회 순서:

```text
1) Redis에서 request_id / 최근 키 조회
2) 없으면 Mongo 이력
3) FE용 DTO로 구간별 latency 계산 후 반환
```

latency 예:

| 구간 | 계산 |
|------|------|
| device → http | `http_received_at - publish_at` |
| http 체류 | `http_forwarded_at - http_received_at` |
| http → consumer | `consumer_received_at - http_forwarded_at` |
| 발행 → DB 적재 | `db_created_at - publish_at` |

### FE

- Redis를 직접 보지 않고 **BE API만** 호출
- 상태: `발행 → HTTP 수신 → 전달 → Consumer → AI → DB`
- 구간 워터폴·막대, 실패 단계 하이라이트

폴링(1~2초)만으로도 적당한 실시간.  
SSE/WS면 더 즉시성이 좋다.

## 8. 전체 한 장

```text
[device]
  publish_at + request_id 붙여 발행
       │
       ▼
[http]
  http_received_at / http_forwarded_at
  stages 1-b, 1-c, 2-a
  → Redis INSERT / UPDATE (request_id)
  → consumer로 전달
       │
       ▼
[consumer / AI]
  consumer_received_at
  추론·처리 후 업무 DB 저장 (created_at)
  → Redis UPDATE (request_id)
  → 완료 시 Mongo에 흐름 이력 flush
       │
       ▼
[BE]  live API (Redis → 없으면 Mongo)
       │
       ▼
[FE]  request_id 기준 파이프라인 실시간 뷰
```

---

## 9. 한 줄 요약

- **추적 키**: `request_id` — 처음 insert, 이후 update
- **핫 경로**: 단계 시각은 **Redis**에만 찍어 DB pool 보호
- **콜드 경로**: 끝나면 **Mongo/DB에 한 방**
- **실시간**: BE가 Redis를 보는 API를 열고, FE는 그 API로 구간·지연을 표시

---

## 10. 미정·후속

- `1-b` / `1-c` / `2-a`의 http 내부 고정 지점(단계 코드표)
- FE 워터폴용 응답 JSON 스키마 확정
- Redis 키 인덱스(최근 N건 목록) 방식
- 완료 flush 주기(즉시 vs 배치)
