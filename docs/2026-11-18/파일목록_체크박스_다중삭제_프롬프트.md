# 파일 목록 체크박스 다중 삭제

## 목표
파일 관리 목록에서 행 체크·전체 선택 후 **선택한 개수만큼** `DeleteAsset`을 호출해 지운다. 지울 수 없는 에셋은 실패로 남기고 넘어가며, 지울 수 있는 에셋은 계속 삭제한다. 끝나면 목록을 다시 불러온다.

## 먼저 읽을 것
1. `README.md` 목적 절
2. `.cursor/skills/apply-guidelines/SKILL.md` (가이드라인은 워킹 트리 밖 읽기만)
3. `lib/src/presentation/features/asset_lookup/asset_lookup_screen.dart` / `asset_lookup_view_model.dart`
4. `lib/src/presentation/core/widgets/catalog_lookup_table.dart` (`actionsBuilder` 패턴)
5. `lib/src/presentation/features/asset_lookup/asset_attach_dialog.dart` 체크·전체 선택 UI 참고
6. `lib/src/domain/use_cases/delete_asset_use_case.dart`
7. 계약: 없음(기존 DeleteAsset)

## 현재 상태
- 목록은 행별 내려받기·삭제만. 선택 Set 없음.
- `deleteAsset`은 1건 삭제 후 `load()`.
- `CatalogLookupTable`은 선택 열 없음(액션 열만 선택적).

## 바꿀 것
1. **CatalogLookupTable** — `actionsBuilder`와 같은 방식으로 선택적 **앞열** 추가: `leadingBuilder`, `leadingHeader`, `leadingFlex`(기본 4). null이면 기존과 동일. 다른 조회 화면 회귀 없음.
2. **ViewModel** — `Set<String> selectedAssetIds`, `selectedCount`, `isSelected`, `didToggleSelected`, `didSetVisibleSelection`(보이는 행 전체 선택/해제), `clearSelection`. `load()` 시작·성공 시 선택 비움.  
   `deleteSelectedAssets()`: 선택 id마다 `_deleteAssetUseCase.execute`를 **순차** 호출. 예외는 모아 두고 다음으로(무시·계속). 한 건이라도 성공하면 마지막에 `load()` 한 번. 반환 `{succeeded, failureNotes}` (화면 InfoBar용). 단건 `deleteAsset` 유지.
3. **화면** — 각 행 Checkbox(체크 시 행 탭으로 상세 가지 않음 — leading은 탭 영역 밖). 헤더 Checkbox = 현재 `visibleRows` 전체 선택(부분 선택은 `checked: null` tri-state, attach 다이얼로그와 동일).  
   `LookupTableHeader`: 선택 `n>0`일 때 보조 버튼 `선택 삭제`(또는 `n개 삭제`). 확인 ContentDialog 후 `deleteSelectedAssets`. 끝나면 선택 해제·InfoBar로 성공/실패 요약(실패 메시지는 서버 문구). 행 단위 삭제는 기존 다이얼로그 유지.
4. **FE 사전 가드 없음** — 삭제 가능 여부는 서버 응답만. 실패 건 skip.

## 유지할 것
- 단건 삭제·내려받기·행 탭→상세
- 다른 CatalogLookupTable 호출(leading 생략)
- DeleteAsset UseCase·repository 계약

## 이번 작업에서 만들지 않음
- 일괄 Delete RPC·병렬 삭제·선택 내려받기·새 UseCase 파일
- CatalogLookupTable을 Widget 셀 전체로 재설계

## 복잡한 코드 제거 및 금지
- 한 화면·한 동작을 위해 새 추상 계층, 전략, 팩토리, 제네릭 헬퍼를 만들지 않는다.
- 같은 역할의 위젯, ViewModel, UseCase, 화면 흐름이 있으면 그것을 쓴다.
- 이번 변경으로 쓰이지 않게 된 분기, 플래그, 래퍼, 죽은 코드는 제거한다.
- 조건 중첩과 모드 플래그 조합으로 경우를 늘리지 않는다.
- 호출을 한 겹 감싸기 위한 파일은 만들지 않는다. 파일 분리는 책임이 분명할 때만 한다.
- 새 상태관리, 새 디자인 시스템, 카드 UI를 도입하지 않는다.
- 프롬프트 범위 밖의 리팩터, 이름 정리, 스타일 통일을 끼워 넣지 않는다.
