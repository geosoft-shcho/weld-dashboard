## 1. 공사

| RPC | 필수 | 동작 |
|---|---|---|
| `CreateProject` | `project.project_no`(앞뒤 공백 없이) | 같은 번호가 있으면 `AlreadyExists` |
| `UpdateProject` | `project.project_id`(또는 `project_no`) | `update_mask`: `project_name`·`site_name`·`customer`. 공사 번호는 못 바꾼다 |
| `DeleteProject` | `project_id`(또는 `project_no`) | 작업이 하나라도 있으면 `FailedPrecondition` |

공사에는 서버가 매기는 숫자 `project_id`가 있고(`Project.project_id`), 작업은 이 번호로 공사에 속한다. 요청에서는 `project_id`와
`project_no` 어느 쪽으로 공사를 가리켜도 되고, 응답의 `Job`에는 둘 다 담겨 온다.
공사 번호는 PDF DB·CARO의 `project_no`와 같은 값이라 등록한 뒤에는 고치지 않는다. 잘못 넣었으면 작업을 옮기거나 지운 뒤
공사를 지우고 다시 만든다.

## 2. 작업

**만들기(`CreateJob`)**

| 칸 | 필수 | 비고 |
|---|---|---|
| `project_no`(또는 `project_id`)·`unit_no`·`item_code` | 필수 | 공백 없이, 정규화된 값(`05`, `TFPB`). `common_key`가 된다. `project_id`를 주면 그 공사의 번호를 쓴다 |
| `joint_no`·`started_at` | 필수 | 이음부와 시작일은 `job_key`에 들어간다 |
| `item_name` | 새 배정이면 필수 | 이미 배정된 품목(공사·호기·품목 코드)이면 안 줘도 되고, 줘도 저장된 이름을 따른다 |
| `job_name`·`item_no`·`operation_no`·`material`·`outer_diameter_mm`·`thickness_mm`·`worker_id`·`ended_at` | 선택 | 나중에 `UpdateJob`으로 채운다 |
| `job_id`·`job_key`·`common_key` | 보내도 무시 | 서버가 정한다 |
| 요청의 `passes` | 선택 | 함께 만들 패스. `pass_no`(1 이상, 서로 달라야 함)만 필수이고 시작·종료 시각도 줄 수 있다(§3의 구간 규칙) |

- 호기·품목 코드는 서버가 정규화하지 않는다. `5호기`를 그대로 보내면 `05`와 다른 품목이 되어 성적서와 이어지지 않는다 —
  `ListJobFilters`가 주는 값을 쓰거나 화면에서 정규화해 보낸다.
- 필수 칸 여섯 가지는 기존 작업 388건이 모두 가진 값이다. 나머지는 원본 자료에 없는 경우가 있어 선택으로 두었다.
- 같은 품목·이음부·날짜로 두 번 만들면 작업이 둘 생긴다(재작업으로 본다). 없는 공사·작업자면 `InvalidArgument`.
- 이미 배정된 품목에 다른 `item_name`을 주면 `InvalidArgument`다(전에는 저장된 이름으로 말없이 바꿨다). 이름을 비우거나 같은 이름을 준다.
- `passes`를 주면 작업과 패스가 한 번에 만들어지고 응답의 `passes`(패스 번호 순)에 번호가 담겨 온다. 패스가 하나라도 틀리면
  작업도 만들어지지 않는다. 만들 때 패스를 모르면 비워 두고 나중에 `CreatePass`로 더한다.

**고치기(`UpdateJob`)**

- `job.job_id` 필수. `update_mask`에 쓸 수 있는 칸: `project_no`(또는 `project_id`), `unit_no`, `item_code`, `job_name`, `item_no`,
  `joint_no`, `operation_no`, `material`, `outer_diameter_mm`, `thickness_mm`, `worker_id`, `started_at`, `ended_at`, `report_set_id`.
- `job_id`는 바뀌지 않는다. 공사·호기·품목·이음부·시작 시각을 고치면 `common_key`와 `job_key`가 따라 바뀐다 — 응답의 `Job`으로
  화면을 갱신한다.
- **성적서 고르기**: 작업은 성적서 세트 하나를 쓴다(`Job.active_report_set_id`).
  - `report_set_id`를 비워 두면 본인 세트(세트의 `common_key`가 작업과 같은 것)를 쓴다 — 품목을 고치면 새 품목의 본인 세트를 본다.
  - 다른 세트를 쓰려면 `update_mask: report_set_id`에 세트 번호(`ListReportSets`로 찾는다). 다른 품목 · 다른 공사의 세트도 되고, 여러 작업이 같은 세트를 골라도 된다. 0을 보내면 지정을 푼다. 없는 세트는 `InvalidArgument`.
  - 고르거나 풀어도 세트 · 다른 작업 · 첨부는 바뀌지 않는다. 잘라 낸 PDF는 첨부가 아니라 세트(`ListReportSets(job_id).split_asset_id`)로 연다.
- 작업 구간을 줄여서 이미 있는 패스가 밖으로 나가게 되면 `InvalidArgument`다. 패스를 먼저 고친다.
- 필수 칸은 비울 수 없고(`InvalidArgument`), 종료는 시작보다 앞설 수 없다. 선택 칸은 마스크에 넣고 값을 비우면 지워진다.
- 첨부·패스·클립은 `job_id`로 달려 있어 그대로 남는다.

**지우기(`DeleteJob`)**

- 패스는 함께 지워진다.
- 첨부, 타임라인(편집한 적이 있는 작업)이 있으면 `FailedPrecondition`이다(고른 성적서 세트는 막지 않는다 — 세트는 남는다). 자료가 붙은
  작업을 실수로 지우지 않게 하려는 것이다 — 먼저 `DetachAsset`·`DeleteTimeline`으로 비운다.

## 3. 패스

| RPC | 필수 | 동작 |
|---|---|---|
| `CreatePass` | `pass.job_id`, `pass.pass_no`(1 이상) | 같은 작업에 같은 번호가 있으면 `AlreadyExists`. 시각은 선택 |
| `UpdatePass` | `pass.pass_id` | `update_mask`: `pass_no`·`started_at`·`ended_at` |
| `DeletePass` | `pass_id` | 그 패스에 붙어 있던 첨부는 작업 공용이 된다(첨부 자체는 남는다) |

**구간 규칙** — 만들 때(`CreateJob`의 `passes`, `CreatePass`)와 고칠 때(`UpdatePass`, `UpdateJob`) 모두 본다.

| 규칙 | 어기면 |
|---|---|
| 패스의 시작·종료는 작업의 시작~종료 안에 있어야 한다(작업 종료가 비어 있으면 시작만 본다) | `InvalidArgument` |
| 한 작업의 패스 구간은 서로 겹칠 수 없다. 앞 패스의 끝과 다음 패스의 시작이 같은 것은 된다 | `FailedPrecondition` |
| 종료는 시작보다 앞설 수 없다 | `InvalidArgument` |

시각이 비어 있는 패스는 겹침을 검사하지 않는다. 겹침 금지는 DB 제약이라 적재기로 넣는 패스에도 적용된다.

패스 구간(`started_at`~`ended_at`)은 타임라인을 패스별로 열 때와 파형을 자를 때 쓰인다. 비워 둘 수 있지만 그 패스로는
구간 조회가 되지 않는다.

### 3.1 품목 배정

공사의 호기에 품목을 배정해 둔다(`tacit.project_item`). 작업 목록 필터와 작업 만들기 화면의 호기·품목 후보가 여기서 나온다.

| RPC | 필수 | 동작 |
|---|---|---|
| `CreateProjectItems` | `project_id`, 줄마다 `unit_no`·`item_code`·`item_name` | 묶음으로 배정. 이미 있는 배정은 같은 이름이면 그 줄을 돌려주고, **다른 이름이면 `InvalidArgument`**(이름을 바꾸려면 `UpdateProjectItem`). 없는 공사·빈 칸도 `InvalidArgument` |
| `UpdateProjectItem` | `item.project_item_id`·`item_name` | 배정 줄의 품목 이름을 고친다. 그 배정을 가리키는 작업 모두에 반영된다 |
| `ListItems` | 없음 | 배정에 쓰인 품목(코드·이름)을 중복 없이. `project_id`를 주면 그 공사, 비우면 전체 공사. 이름을 다시 고르는 추천 목록 |
| `ListJobFilters` | 없음 | 호기·품목을 배정 표에서 읽는다 — 작업이 없는 배정도 나온다. 품목마다 `item_name`·`project_item_id`가 온다 |

- `CreateJob`·`UpdateJob`은 받은 공사·호기·품목 코드의 배정이 없으면 만들고 작업이 그 줄을 가리키게 한다(`Job.project_item_id`, 읽기 전용).
- 품목 이름은 배정 줄마다 따로 둔다. 같은 코드라도 공사·호기에 따라 이름이 달라도 된다.
- 작업을 지워도 배정은 남는다. 공사를 지우면 배정도 지워진다. 배정을 지우는 RPC는 아직 없다.
- 호기·품목 코드·품목 이름은 배정 줄에만 저장한다. 작업의 `unit_no`·`item_code`·`item_name`은 배정 줄에서 읽어 응답에 채운다(proto 필드는 그대로).
- 품목 이름은 `UpdateJob`으로 못 고친다(`InvalidArgument`) — `UpdateProjectItem`으로 고친다. 작업의 호기·품목 코드를 바꾸면 작업이 다른 배정으로 옮겨 간다.

### 3.2 작업자·장비

| RPC | 필수 | 동작 |
|---|---|---|
| `CreateWorker` | `worker.worker_name` | 이름이 같은 작업자도 만들 수 있다(이름에는 유일 제약 없음) — 사번(`employee_no`, 있으면 유일)으로 구분한다 |
| `UpdateWorker` | `worker.worker_id` | `update_mask`: `worker_name`·`worker_type`·`employee_no`·`description`·`inactive`. 이름은 비울 수 없다 |
| `DeleteWorker` | `worker_id` | 작업을 맡은 작업자는 `FailedPrecondition` |
| `CreateEquipment` | `equipment.equipment_name` | `equipment_code`는 선택이고 있으면 유일 |
| `UpdateEquipment` | `equipment.equipment_id` | `update_mask`: `equipment_name`·`line_name`·`equipment_code` |
| `DeleteEquipment` | `equipment_id` | 그 장비로 기록한 에셋이 있으면 `FailedPrecondition` |

- `worker_id`·`equipment_id`는 서버가 매기는 숫자다. 전에 ID로 쓰던 글자(`W-DEV-01`, `DEMO-DEPTH-FRONT`)는 코드로 남아 있다.
- 일괄 적재는 장비를 코드로 찾는다. 적재할 장비의 코드를 바꾸면 적재기 쪽 코드도 같이 바꿔야 한다.
- 작업의 작업자는 `CreateJob`·`UpdateJob`의 `worker_id`로, 에셋의 장비는 업로드의 `equipment_id`로 정한다.

## 4. 에셋 업로드

**2026-10-08 09:40에 운영에 적용했다.** 옛 형식(`POST /assets?file_name=…`, 본문 = 파일 바이트)은 없어졌다.

```
POST /assets
본문: multipart/form-data — metadata(JSON) 파트 다음에 file 파트
응답: 201, {"asset": Asset(GetAsset의 asset과 같은 모양), "runId": "후처리 실행 번호", "warnings": [...]}
```

`metadata`의 값:

| 값 | 필수 | 뜻 |
|---|---|---|
| `jobId` | 선택 | 그 작업에 첨부한다. 없으면 작업 미지정 에셋이 된다(나중에 `AttachAsset`) |
| `passId` | 선택 | 그 패스의 자료로 첨부한다. `jobId`와 함께, 그 작업의 패스여야 한다. 비우면 작업 공통 |
| `equipmentId` | 선택 | 자료를 기록한 장비. 없는 장비면 400 |
| `timeOrigin` | 시간 자료에 필수(아래) | 그 파일의 **시간 0이 가리키는 절대 시각**(RFC 3339). 영상은 첫 프레임, IMU는 깊이 녹화 시작, 회전수는 구간 시작, 패널 · 통합 신호 · 포즈는 첫 샘플 |
| `subject` | 선택 | 주제(글, 길이 제한 없음). 앞뒤 공백만 떼고 저장, `Asset.subject`로 돌아온다. 나중에 고칠 때는 `UpdateAsset` |
| `situation` | 선택 | 상황(글, 길이 제한 없음). 앞뒤 공백만 떼고 저장, `Asset.situation`으로 돌아온다 |

- 번호는 숫자(`128`)나 숫자 글자(`"128"`) 둘 다 받는다. 그 밖의 값(`kind` 등)을 보내면 400 — 종류·MIME·기록 시각·저장 위치는 서버가 정한다.
- **`metadata`가 `file`보다 먼저 와야 한다**(`FormData`에 넣는 순서). 서버는 파일을 받으면서 바로 쓰고, 붙일 곳은 쓰기 전에 확인한다.
- **종류는 파일 내용으로 정한다. 파일 이름·확장자로는 아무것도 판단하지 않는다.** 영상·음성은 스트림 정보, 센서·포즈는 머리행, PDF·이미지는 파일 머리를 본다. 받는 형식은 `AssetService.ListUploadFormats`가 돌려준다(확장자는 파일 선택 창 안내용).
- 어느 형식도 아닌 파일은 종류 없이 등록만 한다(`runId` 없음). 실행 파일은 400.
- **시각은 `timeOrigin`이 늘 이긴다.**

  | 자료 | `timeOrigin` 있음 | `timeOrigin` 없음 |
  |---|---|---|
  | 영상 · 음성 | 첫 프레임 = `timeOrigin` | 파일에 적힌 촬영 시각(`creation_time`, 휴대폰 · 카메라 원본) + `warnings`. 없으면 400 |
  | 깊이 원본 | 첫 프레임 = `timeOrigin` | 400 |
  | IMU(`bag_time_ns`) · 구간초 센서 | `timeOrigin` + 파일의 상대 시각 | 400 |
  | 패널(`절대시각_epoch`) · 통합 신호 · 포즈(`t_abs`) | 첫 샘플 = `timeOrigin`(샘플 간격은 그대로). 파일 시각과 12시간 넘게 다르면 `warnings` | 파일 시각 |

  - 촬영 시각은 기기 시계다 — 녹화 **끝** 시각을 적는 휴대폰(영상 길이만큼 뒤로 놓임), 현지 시각을 UTC로 적는 카메라(9시간 어긋남)가 있다. 화면은 이 경고를 꼭 보이고, 어긋나면 타임라인에서 옮기거나 `timeOrigin`을 넣어 다시 올린다. 우리 장비(액션캠 · 깊이 · wav)의 파일에는 이 값이 없다(2026-10-26 표본).
  - mp4는 촬영 시각이 파일 끝에 있기도 해서, 시각 없는 영상 · 음성의 400은 다 받은 뒤(이어 올리기면 마지막 조각) 나온다 — 이어 올리기면 `POST /assets {uploadId, timeOrigin}`으로 다시 올리지 않고 등록한다.
  - 받은 값은 `properties.upload.time_origin`, 절대 시각 파일의 원래 시각은 `properties.upload.file_start`(차이 `time_origin_diff_s`)에 남는다.
  - **구간 밖이면 알린다**: 작업(`jobId`)에 붙였는데 기록이 패스(`passId`, 없으면 작업 시작 이후) 구간 밖이라 타임라인에 놓이지 않으면 `warnings`에 "구간 밖이라 타임라인에 놓이지 않음 — 첨부는 됐음". 영상 · 음성은 길이까지, 센서 · 포즈는 시작만 보고 판단한다(시작이 패스 끝 뒤일 때). 작업 시작 시각이 없는 작업도 알린다.
  - **올린 뒤 시각 고치기**: `AssetService.UpdateAsset`(`update_mask: recorded_at`). 표준화본도 같이 옮기고, 그 자료의 자동 배치 클립 중 사람이 손대지 않은 것을 지우고 새 시각으로 다시 놓는다(`replace_run_id` — `GetRun`으로 끝을 본다). 사람이 옮기거나 라벨 · 설명 · 관계를 붙인 클립은 그대로다. 비울 수는 없다.
  - 형식마다 꼭 필요한지는 `ListUploadFormats`의 `time_origin_required`(영상 · 음성 · 패널 · 통합 신호 · 포즈는 false — 받을 수는 있다는 뜻이고, 우리 장비 영상은 넣어야 한다).
- 파일은 `YYYY/MM/<asset_id>/<asset_id><확장자>`에 저장한다. 원래 이름은 `file_name`에만 둔다.
- 오류: 값이 틀리면 400(본문에 사유), 한도를 넘으면 413, 그 밖은 500. 한도는 `MEDIATAG_UPLOAD_MAX_BYTES`(기본 8GiB)이고 `ListUploadFormats`의 `max_bytes`로도 온다.
- 끊기면 처음부터 다시 올린다(이어받기 없음). 같은 파일을 다시 올리면 새 에셋이 된다(중복은 `ListDuplicateAssets`).

### 4.1 후처리

올리면 내장 도구 `asset-postprocess`의 실행이 큐에 들어가고(`runId`), 서버 안 워커가 차례로 한다.

| 순서 | 하는 일 | 대상 |
|---|---|---|
| 1 | 파일 속성(해상도·코덱·쪽 수·열 이름) | 종류가 정해진 것 전부 |
| 2 | 길이 | 영상·음성·깊이 원본 |
| 3 | 표준화(`t_ns` + 채널 CSV). 표준화본이 원본의 첨부 자리를 물려받는다 | 센서·포즈 |
| 3 | 글자 인식(OCR): 전용 서버(pdf-to-text)에 보낸다. 성적서 양식이면 세트 나누기 → 잘라 낸 PDF·섹션까지, 아니면 추출 결과만 남긴다. 쪽 수에 따라 몇 십 초~20분 | PDF 전부 |
| 4 | 타임라인 배치(기록 시각대로, 패스 구간 안으로 자름) | **올린 자료 자신**(센서·포즈는 그 표준화본). 작업에 첨부된 영상·음성·센서·포즈일 때 |

- 상태는 `ToolService.GetRun(run_id)`로 본다(`wait_for_terminal`로 끝날 때까지 기다릴 수 있다). 실패한 실행은 `StartRun`(도구 `asset-postprocess`, 대상 = 그 에셋)으로 다시 건다.
- 단계마다 이미 한 일은 건너뛰어, 다시 돌려도 결과가 겹치지 않는다.
- 실패하면 3번까지 다시 시도한다(`ToolRun.attempt_count`). 서버가 실행 도중 멈추면 다시 뜰 때 이어서 돌린다. 한도·워커 수는 `MEDIATAG_RUN_MAX_ATTEMPTS`(3)·`MEDIATAG_RUN_WORKERS`(2).
- **첨부와 배치는 다르다.** 첨부(`AttachAsset`)는 "이 작업의 자료"라는 표시이고 타임라인을 건드리지 않는다. 배치는 클립이다(`CreateClip` — 첨부 안 된 에셋을 놓으면 작업 공통으로 자동 첨부된다). 업로드의 자동 배치는 올린 그 자료 하나만 놓는다 — 이미 놓여 있으면 건너뛰고, 그 작업의 다른 자료(첨부만 해 둔 것, 타임라인에서 지운 것)는 놓지 않는다. 지운 자료를 다시 기록 시각대로 놓으려면 그 에셋으로 후처리를 다시 건다.
- **타임라인을 편집하는 중에도 올릴 수 있다.** 후처리는 클립을 새로 놓기만 하고 이미 있는 클립·트랙은 건드리지 않는다. 같은 트랙에서 시간이 겹치면 `<트랙> (2)` 트랙에 놓는다. 화면은 실행이 끝난 뒤 타임라인을 다시 불러와야 새 클립이 보인다.
- **성적서인지는 올리는 사람이 고르지 않는다.** PDF는 모두 글자 인식에 보내고, 성적서 양식으로 판별된 구간이 있으면 성적서 세트가 만들어진다. 일반 문서는 추출 결과(`ocr_json`)만 파생 에셋으로 남는다. 한 번 인식한 PDF는 후처리를 다시 걸어도 다시 보내지 않는다.
- 성적서를 `jobId`와 함께 올리고 **세트가 하나** 나오면 그 세트의 본인 품목이 그 작업의 품목(`common_key`)이 된다 — 그 품목의 작업 중 세트를 고르지 않은 작업(이음부마다 하나)이 모두 이 세트를 쓴다. 첨부로 복사하지 않고, 원본 PDF는 올릴 때 정한 작업에만 첨부된다. 세트가 **여럿**(호기 묶음)이거나 `jobId` 없이 올리면 본인 품목 없이 두고, 작업마다 `UpdateJob(report_set_id)`로 고른다. 이음부별 결과(UT·MT 표)는 그 작업이 쓰는 세트 안의 확인번호(`DGT-ELA-01` 꼴)와 작업의 `joint_no`가 같은 것끼리 이어진다(`ListQualityResults`).
- 깊이 원본은 타임라인에 놓지 않는다(그릴 방법이 없다). 작업·패스 구간 밖의 자료도 놓지 않는다.
- 트랙 이름은 `장비 · 자료 계열`(예: `앞 카메라 · imu`)이다. 계열은 내용으로 정한다: `video`, `audio`, `imu`, `rpm`, `panel`, `signals`, `pose2d`, `pose3d`.
- 음성 추출(`audio-extract`)도 같은 큐로 옮겼다. `StartRun`은 `queued`를 돌려주고 워커가 바로 꺼내 돌린다.

### 4.2 성적서 문서별 PDF와 나중에 붙이기

원본 PDF → 문서(양식 한 건)별 PDF(파생 에셋) → 작업 첨부로 이어진다. 영상에서 음성을 뽑거나 센서를 표준화하는 것과 같은 모양이다.

| 파일 | 만들어지는 때 | 작업에 붙는 때 |
|---|---|---|
| 올린 원본 PDF | 업로드 | 올릴 때 정한 작업에만 |
| 세트 묶음 PDF(품목 하나의 문서들) | 글자 인식 뒤, 품목별 문서가 있을 때 | 붙이지 않는다 — 작업이 쓰는 세트의 `split_asset_id`로 연다 |
| 문서별 PDF | 글자 인식 뒤, 문서마다 하나 | 세트 밖 문서(표면처리·도장)는 올릴 때 정한 작업에(첨부만). 그 밖은 사람이 붙일 때 |

- 문서별 PDF의 번호는 세트 조회의 섹션마다 온다(`SectionSummary.asset_id`, `Section.asset_id`). 에셋 트리에서는 원본 PDF의 자식이다.
- **문서 PDF를 `AttachAsset`으로 붙이면 첨부 한 줄만 생긴다.** 세트에 이어지거나 같은 품목의 다른 작업에 퍼지지 않는다 — 세트는 추출된 그대로다. 성적서 판정을 바꾸려면 세트를 고른다(§2 `report_set_id`).
- 표면처리·도장 문서처럼 품목 여럿을 묶은 문서는 필요한 작업에 각각 붙인다.
- `AttachAsset`은 타임라인을 건드리지 않는다.
- 세트 묶음 PDF는 당분간 그대로 둔다(같은 쪽이 세트 PDF와 문서 PDF 두 곳에 있다).

예(브라우저):

```js
const form = new FormData();
form.append("metadata", JSON.stringify({ jobId, passId, equipmentId, timeOrigin: "2026-09-16T13:38:53+09:00" }));
form.append("file", file);            // metadata 다음에
const { asset, runId, warnings } = await (await fetch(`${base}/assets`, { method: "POST", body: form })).json();
```

### 4.3 이어 올리기(큰 파일 · 외부망)

multipart(§4)는 끊기면 처음부터 다시 올린다. 큰 파일(깊이 원본 4~12GB)이나 외부망은 파일을 조각내 보내고 끊긴 데부터 잇는 **tus 1.0** 규격으로 받는다.
**마지막 조각을 받으면 서버가 바로 등록**하고, 그 응답에 §4와 같은 결과(`asset` · `runId` · `warnings` · `duplicateOf`)를 준다.

| 요청 | 하는 일 |
|---|---|
| `POST /uploads` | 시작. `Upload-Length`(전체 바이트) 필수. `Upload-Metadata`에 `filename` 필수, `metadata`(§4의 값을 JSON으로) 선택. **metadata를 여기서 검사한다** — 없는 작업 · 남의 패스 · 틀린 시각은 올리기 전에 400 |
| `PATCH /uploads/{id}` | 조각(`Upload-Offset`부터). **첫 조각**에서 앞부분을 검사한다 — 실행 파일 · `timeOrigin` 없는 영상 · 음성이면 400이고 업로드를 지운다(새로 시작). **마지막 조각**이면 등록하고 200 + 등록 결과(JSON) |
| `HEAD /uploads/{id}` | 어디까지 받았나(`Upload-Offset`). 이미 등록한 업로드는 다 받았다고 답한다 |
| `DELETE /uploads/{id}` | 취소 |
| `POST /assets` (`Content-Type: application/json`) | 예비 — 마지막 응답을 못 받았거나 등록이 실패했을 때. 아래 |

- 위 네 요청은 `tus-js-client`(MIT, v4 이상)가 알아서 보낸다 — 화면은 주소 · `filename` · `metadata`만 준다.
- metadata는 시작할 때 정해진다. 올리는 도중 화면에서 바꾼 값은 반영되지 않는다(주제 · 상황은 등록 뒤 `UpdateAsset`).
- 한도는 multipart와 같은 값(파일 하나 기준, `ListUploadFormats.max_bytes`).
- sha256은 받으면서 계산해 큰 파일도 마지막 응답이 곧 온다(서버가 중간에 재시작된 업로드만 다 받은 뒤 다시 읽어 12GB에 2분쯤).
- 여러 파일은 파일마다 따로 시작한다(동시에 2~3개 권장). 대기열 · 동시 개수 · 일시정지는 화면이 관리한다.
- 탭을 닫으면 멈춘다. 같은 파일을 다시 고르면 `tus-js-client`의 `findPreviousUploads()`로 받은 데부터 잇는다.
- 등록하지 않은 업로드와 등록 결과는 마지막 조각을 받은 뒤 72시간이 지나면 지운다.

**마지막 응답을 받지 못했을 때 · 등록이 실패했을 때 (`POST /assets`)**

| 경우 | 화면이 보는 것 | 할 일 |
|---|---|---|
| 마지막 응답 전에 끊김 → 다시 이음 | `onSuccess`의 응답 본문이 빔(HEAD가 다 받았다고 답함) | `POST /assets` `{"uploadId"}` → 이미 등록된 결과를 준다 |
| 다 받았지만 등록이 실패(예: 시간 자료인데 `timeOrigin` 없음) | 마지막 조각이 400 + 이유 | metadata를 고쳐 `POST /assets` `{"uploadId", ...metadata}` → 등록. 파일을 다시 올리지 않는다 |
| 서버 오류(500)로 등록 실패 | 마지막 조각이 500 → 다시 시도 뒤 본문 없는 성공 | `POST /assets` `{"uploadId"}` → 시작할 때의 metadata로 등록 |

- `{"uploadId"}`만 보내면 시작할 때의 metadata를, metadata 값을 같이 보내면 그 값을 쓴다. 응답은 §4와 같다(201).
- `uploadId`는 업로드 주소(`upload.url`)의 마지막 조각.

예(브라우저):

```js
import * as tus from "tus-js-client";

const meta = { jobId, passId, equipmentId, timeOrigin, subject, situation };  // 파일마다(공통 기본값 + 파일별 수정)
const upload = new tus.Upload(file, {
  endpoint: `${base}/uploads/`,
  chunkSize: 64 * 1024 * 1024,                 // 조각 크기(끊기면 이 단위로 다시 보냄)
  retryDelays: [0, 3000, 10000, 30000],        // 끊기면 자동으로 이어 올림
  metadata: { filename: file.name, metadata: JSON.stringify(meta) },
  onProgress: (sent, total) => setProgress(sent / total),
  onError: (err) => showError(err.originalResponse?.getBody() ?? err.message),  // 400이면 이유 문구
  onSuccess: async ({ lastResponse }) => {
    let body = lastResponse.getBody();
    if (!body) {                                // 마지막 응답을 못 받고 이어서 끝난 경우
      const uploadId = upload.url.split("/").pop();
      body = await (await fetch(`${base}/assets`, {
        method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ uploadId }),
      })).text();
    }
    const { asset, runId, warnings, duplicateOf } = JSON.parse(body);
  },
});
upload.start();
```

### 4.4 파일 한 줄 상태(업로드 + 후처리)

업로드와 후처리는 서버에서 따로 돈다(후처리는 서버 큐 — 동시 2개, 실패하면 3번까지 다시). 화면은 아래 신호를 이어 붙여 파일마다 상태 하나로 보인다.
서버 변경 없이 된다.

| 화면 상태 | 신호 | 다음 |
|---|---|---|
| 업로드 중 n% | `tus-js-client` `onProgress(보낸, 전체)` | 마지막 응답 |
| 실패(이유) | 시작 · 첫 조각 · 마지막 조각의 4xx 본문 | 끝(고쳐서 다시) |
| 등록됨 | 마지막 응답(§4.3)의 `asset` · `runId` · `warnings` · `duplicateOf` | `runId`가 비면 → 완료 |
| 후처리 대기(n번째) | `GetRun` `status = RUN_STATUS_QUEUED`, `queue_position` | 다시 `GetRun` |
| 처리 중 | `status = RUN_STATUS_RUNNING` (`progress_percent`는 진행 신호를 주는 단계만, 없으면 0) | 다시 `GetRun` |
| 완료 | `RUN_STATUS_SUCCEEDED` — 파생 Asset은 `output_asset_ids` | 끝 |
| 후처리 실패(이유) | `RUN_STATUS_FAILED` — `error_message`. 파일은 등록된 채로 남는다 | `StartRun`으로 다시 걸 수 있음 |
| 취소됨 | `RUN_STATUS_CANCELED` | 끝 |

- 걸리는 시간(운영 실측): 센서 · 영상 · 포즈 등은 후처리가 0~8초라 "등록됨 → 완료"가 거의 바로 이어진다. **성적서 PDF는 글자 인식 때문에 15~20분** "처리 중"이 보인다.
- `GetRun`은 `wait_for_terminal: true`면 끝날 때까지(최대 `wait_timeout_seconds`, 기본 30 · 최대 600초) 붙잡았다가 끝나는 즉시 답한다 —
  끝나는 순간을 바로 알고 요청 수도 적다. 대기 순번 · 처리 중을 보이려면 그 사이 몇 초마다 `wait_for_terminal` 없이 불러도 된다.
- `warnings`(중복 · 시각 차이 등)는 등록됐을 때 한 번 오니 완료 뒤에도 보이게 들고 있는다.
- 탭을 새로 열었으면 `runId`를 잃는다 — 그 Asset의 실행은 `ListRuns(target.asset_id)`로 찾는다(생성 순, 마지막이 최신).

예(파일 하나):

```js
async function uploadOne(file, meta, setRow) {           // setRow({ state, percent, message, asset, warnings })
  const result = await new Promise((resolve, reject) => { /* §4.3의 tus.Upload — onProgress에서 setRow({ state: "업로드 중", percent }) */ });
  const { asset, runId, warnings } = result;
  setRow({ state: "등록됨", asset, warnings });
  if (!runId) return setRow({ state: "완료", asset, warnings });
  for (;;) {
    const { run } = await toolClient.getRun({ runId, waitForTerminal: true, waitTimeoutSeconds: 60 });
    switch (run.status) {
      case RunStatus.QUEUED:    setRow({ state: `후처리 대기(${run.queuePosition}번째)` }); break;
      case RunStatus.RUNNING:   setRow({ state: "처리 중", percent: run.progressPercent }); break;
      case RunStatus.SUCCEEDED: return setRow({ state: "완료", asset, warnings });
      case RunStatus.FAILED:    return setRow({ state: "후처리 실패", message: run.errorMessage, asset, warnings });
      case RunStatus.CANCELED:  return setRow({ state: "취소됨", asset, warnings });
    }
  }
}
```
