# 관리 화면 구성과 서버 추가 안내

대시보드에 공사·작업·에셋·작업자·장비 관리 화면을 넣을 때의 화면 구성과, 그 화면을 위해 mediatag에 더해야 할 RPC를 정리한다. 정본 아님.
화면안은 같은 폴더의 `관리 화면안.html`(브라우저로 바로 열림)이고, 아티팩트 「공사 관리 화면안」(https://claude.ai/artifact/XGm9652WqzCz9kYLT5Bpbx, 비공개 — 공유해야 열린다)으로도 올라가 있다. 이 문서는 그 화면안을 글로 옮긴 것이다.
지금 있는 RPC의 자세한 동작은 `공사·작업·패스 관리와 업로드 안내.md`에 있다. 이 문서는 화면 쪽 흐름과 **새로 필요한 것**만 적는다.

## 1. 공통

**메뉴 위치.** 왼쪽 아이콘 줄에 "관리"를 하나 더하고 그 안을 공사 · 작업 · 에셋 · 작업자 · 장비 탭으로 나눈다. 지금 메뉴(수집 모니터링 · 작업 이력 조회 · 파형 비교 · 성적서)는 조회용이라, 고치고 지우는 화면을 따로 모으는 게 덜 헷갈린다. 주소는 `#/admin/project`, `#/admin/job`, `#/admin/asset`, `#/admin/worker`, `#/admin/equipment`처럼 탭마다 둔다.

**만드는 순서.** 공사 → 작업 → 에셋. 작업은 공사와 배정이 있어야 만들고, 에셋은 작업이 있어야 붙인다. 작업자와 장비는 따로 먼저 만들어 둔다 — 작업자는 작업의 [작업자] 칸에서, 장비는 올리기 창의 [장비] 칸에서 고른다(둘 다 비워도 된다).

**목록 검색.** 공사 · 작업자 · 장비는 몇 건뿐이라(2026-10-15 운영 DB: 공사 9 · 작업자 8 · 장비 4) 목록을 한 번에 받아 **화면에서 거른다**. 검색 칸 하나에 친 글자를 여러 칸에 부분 일치(대소문자 · 앞뒤 공백 무시)로 찾고, 서버 필터는 두지 않는다. 수백 건이 넘어 느려지면 그때 서버에 `query` 필터를 더한다.

**탭 사이 이동 — 필터를 채워 연다.** 공사 → 작업 → 에셋으로 내려갈 때 다음 탭의 필터를 채운 채로 연다. 서버 수정 없음(기존 필터).

| 어디서 | 누르는 것 | 열리는 탭과 필터 | 주소 |
|---|---|---|---|
| 공사 상세 | 작업 n건 옆 [작업 탭에서 보기 →] | 작업 탭, 공사 = 이 공사 → `ListJobs(project_id)` | `#/admin/job?project_id=7` |
| 공사 상세 배정 줄 | [작업 →] | 작업 탭, 공사 · 호기 · 품목 → `ListJobs(project_id, unit_no, item_code)` | `#/admin/job?project_id=7&unit_no=01&item_code=LD-C` |
| 작업 상세 첨부 칸 | [에셋 탭에서 보기 →] | 에셋 탭, 작업 = 이 작업 → `ListJobAssets(job_id)` | `#/admin/asset?job_id=388` |
| 작업 상세 패스 칸 | 패스 줄의 [에셋 →] | 에셋 탭, 작업 · 패스 → `ListJobAssets(job_id, pass_id)` | `#/admin/asset?job_id=388&pass_id=818` |

- 넘긴 필터 밖의 칸(작업자, 종류 · 파일 이름 · 장비 · 작업 미지정만)은 비운다 — 넘어간 탭에서 이유 모르게 빠지는 행이 없게.
- 열린 탭의 필터 패널에 넘긴 값이 그대로 보이고, 거기서 바로 풀거나 바꾼다. 따로 "어디서 왔음" 표시는 두지 않는다.
- 고른 항목이 새 목록에 없으면 첫 행을 고른다.
- 필터는 주소에 남긴다(위 표). 이동은 주소를 바꾸는 것(`pushState`)으로 해서 브라우저 [뒤로]가 앞 탭 · 앞 필터로 돌아가게 하고, 새로 고쳐도 · 링크로 보내도 같은 목록이 보이게 한다. 화면안은 탭 이름만 주소에 쓴다(필터는 오른쪽 기록 칸에 주소 꼴로 남김).
- 반대 방향(에셋 → 붙은 작업 §5.2, 작업자 · 장비 → 작업)은 행을 누르면 그 작업으로 가는 지금 방식 그대로다.

**화면 모양.** 기존 화면과 같게 위 필터 패널, 왼쪽 표, 오른쪽 상세 패널. 첫 화면에서 스크롤 없이 다 보이게 하고 표와 상세만 안에서 스크롤한다.

**시각 입력.** 작업 · 패스의 시작 · 종료와 업로드의 `timeOrigin`은 **밀리초까지** 받는다.

- `<input type="datetime-local" step="0.001">`. 크롬 · 엣지는 ms 칸이 생기고, 사파리는 안 생긴다(사파리를 지원하려면 ms 칸을 따로 둔다).
- 보낼 때는 입력값에 `+09:00`을 붙여 `2026-10-30T08:29:16.250+09:00` 꼴로 만든다. `new Date()`를 거치면 브라우저 시간대가 끼어든다.
- 서버(`google.protobuf.Timestamp`, 나노초)와 DB(`timestamptz`, 마이크로초)는 ms를 그대로 저장한다 — 고칠 것 없음.

**부르는 수.** 탭을 열 때 · 고를 때 부르는 것을 줄인다. 아래 2~4는 서버 수정 없이 화면만으로 된다.

| 탭 | 지금(운영 DB 수 기준) | 줄인 뒤 |
|---|---|---|
| 공사 | `ListJobFilters` + 공사마다 작업 수 `ListJobs` 9 = 10 | 1(다른 탭과 같이 씀) |
| 작업자 | `ListWorkers` + 작업자마다 `ListJobs` 8 = 9 | 0 |
| 장비 | `ListEquipment` + 장비마다 `ListJobs` 4 · `ListAssets` 4 = 9 | 0 |
| 작업 | `ListJobFilters` · `ListJobs` + 고를 때 `GetJob` · `ListJobAssets` = 4 | `ListJobs` · `GetJob` = 2(첨부 칸을 열 때 +1) |
| 에셋 | `ListAssets` + 고를 때 `GetAsset` · `ListJobs(asset_id)` = 3 | 2 |

1. **개수는 `ListJobFilters` 한 번에**(§5.9, 서버). 지금 부르는 수의 대부분이 목록 행마다 `ListJobs(page_size=1)`로 개수를 세는 것이다. `ListJobFilters`는 이미 공사 · 작업자 · 장비 목록을 함께 주므로, 개수만 더하면 세 탭이 이 한 번으로 그려진다. §5.9 전에는 지금처럼 행마다 센다.
2. **받은 것을 탭끼리 같이 쓴다.** `ListJobFilters` 결과는 앱 전체에 하나만 들고, 공사 → 작업 → 에셋으로 넘어갈 때 다시 부르지 않는다. 작업자 · 장비 탭도 이 안의 `workers` · `equipment`를 쓴다(`ListWorkers` · `ListEquipment`는 부르지 않는다). 다시 부르는 때는 아래 "여러 사람이 쓸 때"와 공사 · 배정 · 작업 · 작업자 · 장비를 만들거나 지운 뒤.
3. **고친 결과는 응답으로 바로 반영한다.** `UpdateJob` → `Job`, `Create`/`UpdateProject` → `Project`, `CreateProjectItems` · `UpdateProjectItem` → 배정, `AttachAsset` → `JobAsset`, `Create`/`UpdateWorker` · `Equipment` → 그 행. 지우기 · `DetachAsset`은 응답이 비어 있으니 성공하면 그 행만 뺀다. 목록을 통째로 다시 부르지 않는다.
4. **필요할 때만 부른다.**
   - 작업 상세: `GetJob`은 패스 때문에 부른다(목록 행엔 패스 수만). `ListJobAssets`는 첨부 칸을 열 때만, 작업별로 들고 있는다.
   - 에셋 상세: `ListAssets`의 행이 이미 `Asset` 전체라 `GetAsset`을 부르지 않는다. 링크로 들어와 목록에 없는 에셋일 때만 부른다.
   - 에셋 파일 이름 검색: 친 뒤 300ms 기다렸다 부르고, 앞 요청은 `AbortController`로 취소한다.

작업 상세를 한 번에 주는 RPC(`GetJob` + `ListJobAssets`)는 두지 않는다 — 첨부 칸을 열 때만 부르면 충분하다.

**여러 사람이 쓸 때.** 서버가 모든 검사를 다시 하므로 데이터가 깨지지는 않는다. 받아 둔 목록이 늦을 뿐이라 다음 둘을 지킨다.

- **다시 받기**: 탭에 들어올 때나 브라우저 창으로 돌아올 때(`visibilitychange`), 받은 지 30초가 넘었으면 `ListJobFilters`를 다시 부른다. 1번 덕분에 한 번이면 된다.
- **막히면 다시 받기**: 다른 사람이 먼저 바꿔 화면 값이 옛것이면 서버가 막는다 — 지우기 버튼이 켜져 있었지만 그사이 작업이 생김(`FailedPrecondition`), 이미 지워짐(`NotFound`), 번호 · 코드가 겹침(`AlreadyExists`), 패스가 겹침. 이 오류가 오면 서버 문구를 보이고 그 목록 · 상세를 다시 부른다. 화면이 먼저 막는 검사는 편의일 뿐이다.
- 같은 칸을 동시에 고치면 나중 저장이 이긴다(`update_mask`로 바뀐 칸만 보내니 다른 칸끼리는 둘 다 남는다). 지금은 이대로 둔다 — §6.
- 실시간 알림(서버 푸시)은 두지 않는다.

**지우기 확인.** 지우기는 모두 되돌릴 수 없다. 서버가 막는 경우(`FailedPrecondition`)는 화면이 아는 값으로 먼저 막고 이유를 보여 준다. 공사는 공사 번호를 다시 입력해야 지워지게 한다.

- 호기만 따로 만들 수 없다 — 호기는 배정 줄에만 있다.
- 호기 `5`는 서버가 `05`로 맞춘다. 품목 코드는 공백을 빼고 대문자로 보낸다.

## 3. 작업 탭

**표는 "작업 이력 조회"의 것을 그대로 쓴다**(같은 필터 · 같은 `ListJobs`). 관리 탭은 오른쪽 상세 패널과 "+ 새 작업"만 더한다. 이력 조회의 [상세]는 관리 > 작업으로 이어 준다.

상세 패널은 기본 정보 · 패스 · 첨부 세 칸이다.

| 화면 동작 | RPC | 비고 |
|---|---|---|
| 목록 · 필터 | `ListJobFilters`, `ListJobs` | 공사 · 호기 · 품목 · 작업자. 이력 조회의 표 그대로 |
| 새 작업(패스 포함) | `CreateJob` | 아래 "새 작업 창" |
| 상세 · 기본 정보 수정 | `GetJob`, `UpdateJob` | 공사 · 호기 · 품목 코드 · 이음부 · 시작 · 종료 · 작업자 · 작업 이름. 바뀐 칸만 `update_mask` |
| 작업 지우기 | `DeleteJob` | 첨부 · 타임라인 · 직접 매칭한 성적서 세트가 있으면 막힘 |
| 패스 추가 · 수정 · 지우기 | `CreatePass` · `UpdatePass` · `DeletePass` | 작업 구간 안, 서로 안 겹침. 지운 패스의 첨부는 공용이 됨 |
| 첨부 보기 | `ListJobAssets` | 패스 · 공용 |
| 이 작업에 올리기 | `POST /assets` | 올리기 창(§4)에 작업이 채워진 채로 |
| 에셋 붙이기 | `AttachAsset` | 에셋 번호 · 패스 |
| 첨부 패스 바꾸기 | `AttachAsset` | 패스 칸에서 바로. 아래 "첨부 고치기" |
| 떼기 | `DetachAsset` | 클립 · 성적서 세트가 쓰면 막힘 |
| 에셋 보기 | `ListJobAssets(job_id[, pass_id])` | 에셋 탭으로 필터를 채워 이동(§1 "탭 사이 이동") |

**첨부 고치기.** 첨부(`tacit.job_asset`)에서 고칠 값은 패스 하나다(작업 · 에셋은 첨부의 열쇠).

- **패스 바꾸기**: 첨부 표의 패스 칸을 고르는 칸(공용 · 1패스 · 2패스 …)으로 두고, 바꾸면 `AttachAsset(job_id, asset_id, pass_id)`를 다시 보낸다. 이미 붙어 있으면 `pass_id`만 고친다(upsert). 0 = 작업 공용. 다른 작업의 패스면 `InvalidArgument`. **서버 수정 없음.**
- **다른 작업으로 옮기기**는 따로 두지 않는다 — 새 작업에 [에셋 붙이기], 원래 작업에서 [떼기]. 클립 · 성적서 세트가 쓰는 첨부는 떼기가 `FailedPrecondition`이라, 옮길 때는 떼기가 되는지 먼저 본다.
- 패스를 지우면 그 패스의 첨부는 저절로 공용이 된다(외래 키 `ON DELETE SET NULL`).

첨부 칸 [에셋 탭에서 보기 →]와 패스 줄 [에셋 →]는 에셋 탭의 작업 필터(§4)를 채워 연다(§1 "탭 사이 이동"). 첨부 칸은 평평한 표이고, 파생 트리 · 미리 보기 · 종류 거르기는 에셋 탭에서 본다.

**새 작업 창 — 패스를 줄로 함께 넣는다**(공사 만들 때 품목 줄을 넣는 것과 같다).

```
공사 *   [EX006 ▼]          호기 · 품목 * [01 · LD-C LEG DIAGONAL "C" ▼ / + 새 배정]
이음부 * [DGT-ELC-02]       작업자 [미지정 ▼]
시작 *   [2026-10-30 08:16:00.000]   종료 [2026-10-30 09:04:14.100]

패스  시작                       종료
[1]   [2026-10-30 08:16:00.000] [2026-10-30 08:29:16.300]  ✕
[2]   [2026-10-30 08:29:16.300] [                       ]  ✕
+ 패스 추가
```

- 첫 줄은 1패스이고, 작업 시작을 넣으면 1패스 시작이 같은 값으로 채워진다.
- "+ 패스 추가"는 다음 번호를 넣고 시작을 앞 패스의 종료로 채운다.
- 시각은 비워도 된다(번호만 만든다). 줄을 다 빼면 패스 없이 만든다.
- 만들기 전에 화면에서 검사한다: 번호 1 이상 · 서로 다름, 종료 ≥ 시작, 작업 구간 안, 서로 안 겹침(맞닿는 건 됨).
- 보내는 것은 `CreateJob` 한 번이다 — `job`과 `passes[{pass_no, started_at, ended_at}]`. 서버도 같은 검사를 하고, 하나라도 틀리면 작업도 안 만들어진다. 응답의 `passes`에 `pass_id`가 온다. **서버 수정 없음.**

화면 규칙

- 필수는 공사 · 호기 · 품목 코드 · 이음부 · 시작. 새 배정이면 품목 이름도 필수.
- 호기 · 품목 코드는 `ListJobFilters`가 준 값을 고르게 한다. 새 배정을 직접 칠 때는 화면이 정규화해 보낸다.
- 공사 · 호기 · 품목 · 이음부 · 시작을 고치면 공통키와 작업 키가 다시 만들어진다 — 응답의 `Job`으로 화면을 갱신한다.
- 품목 이름은 작업 탭에서 못 고친다(공사 탭에서).
- 작업 구간을 줄여 패스가 밖으로 나가면 `InvalidArgument`. 화면에서 "n패스를 먼저 고치세요"로 막는다.
- 작업 지우기는 첨부 · 타임라인 · 직접 매칭한 성적서 세트가 있으면 막힌다. 첨부 수와 성적서 여부는 목록 행에 있지만 타임라인 여부는 없다(§5.6).

**펼치기(하위 탐색).**

- ▸는 **처음 펼칠 때 한 번** `ListAssets(parent_asset_id, page_size=50)`를 부르고, 결과를 부모별로 들고 있는다. 접었다 다시 펴면 부르지 않는다. 올리기 · 지우기 · 합치기를 하면 그 부모의 결과를 버리고 다음 펼칠 때 다시 부른다.
- 자식이 많은 부모가 있다(성적서 `1호기.pdf` 101은 잘라 낸 파생이 217개). 50개를 넘으면 부모 아래 마지막 줄에 [더 보기]를 두고 `page_token`으로 이어 받는다.
- 펼치거나 행을 골라도 **표의 스크롤은 그대로 둔다**. 표를 통째로 다시 그리는 구현이면 그리기 전 `scrollTop`을 저장했다 되살린다(화면안이 이렇게 한다). 상세 칸은 다른 항목을 고르면 맨 위에서 시작한다.

**작업 필터.** 필터 패널에 작업 · 패스 칸을 둔다. 작업을 고르면 `ListAssets` 대신 `ListJobAssets(job_id)`를 부르고, 패스를 고르면 `pass_id`(0 = 작업 공용만)를 더한다.

- 작업 칸은 작업 탭 필터처럼 공사 → 호기 → 품목 → 이음부(`ListJobFilters`) → 작업(`ListJobs`, 재작업이 있어 날짜를 같이)으로 좁힌다.
- `ListJobAssets`는 페이지 없이 다 준다. 작업 하나의 첨부는 많지 않아서(운영 DB 2026-10-15: 평균 48 · 최대 386) 한 번에 받고, 종류 · 파일 이름 · 장비는 화면에서 거른다. "작업 미지정만"은 끈다(서로 반대 조건).
- 서버에서 함께 걸러야 할 일이 생기면(여러 작업, 페이지) `ListAssetsRequest.job_id = 8`(§5.2와 같은 `EXISTS` 조건)을 더한다. 지금은 두지 않는다.

**작업 필터에서의 계층.** `ListJobAssets`는 계층 없는 목록이지만 `Asset`마다 `provenance.parent_asset_id` · `child_count`가 있어 화면이 트리를 짠다. 운영 DB(2026-10-15)에서 작업에 붙은 파생 668건은 이렇다.

| 만든 방법 | 부모도 같은 작업에 붙음 | 부모는 안 붙음 | 화면 |
|---|---|---|---|
| 포즈 · STT | 105 | 0 | 목록 안 부모 아래로(▸) |
| `pdf_split`(잘라 낸 PDF) | 0 | 360 | 맨 위 줄 + "원본 101 · 1호기.pdf(이 작업에 첨부 안 됨)" 링크 — 부모는 어느 작업에도 안 붙어 있다. §5.8 뒤에는 펼쳐서 문서별 PDF → OCR · 그림까지 내려간다 |
| `timeseries_normalize`(표준화본) | 0 | 203 | 맨 위 줄 — 원본 대신 표준화본이 붙어 있다 |

1. 부모가 같은 목록에 있으면 그 아래로 넣는다.
2. 없으면 맨 위 줄로 두고 부모를 링크로 보인다(누르면 부모 상세).
3. 부모의 `child_count`가 목록 안 자식 수보다 크면 첨부 안 된 파생이 있다(운영 DB 6건, 영상의 STT · 포즈). 펼칠 때만 `ListAssets(parent_asset_id)`를 불러 **이미 있는 행은 빼고** "첨부 안 된 파생"으로 보인다. 그냥 ▸마다 `ListAssets(parent_asset_id)`를 이으면 목록에 있는 자식이 두 번 나온다.
4. 종류 · 이름 필터로 부모가 빠지면 그 자식은 맨 위 줄로 올라온다.

기본 목록(`ListAssets`, 원본만 맨 위)에서는 잘라 낸 PDF · 표준화본이 부모 아래 숨지만, 작업 필터에서는 맨 위로 온다 — 그 작업에 실제로 붙은 것이 이것들이다.

**상세 — 미리 보기와 정보.**

- **정보는 서버가 준 표시 목록(`Asset.display`, §5.7)을 그대로 그린다.** 종류마다 `properties` 키가 다르고 빠진 값도 있어서(문서 2302는 비어 있음), 화면이 키를 해석하지 않게 한다. 원래 `properties`는 접어서 둔다.
- **미리 보기는 화면이 `kind`로 고르고 `content_url`로 연다.** 같은 종류라도 형식에 따라 다르다.

| kind | 미리 보기 |
|---|---|
| 영상 · 음성 | 플레이어. 영상은 `start_time_ns`부터(`타임라인 그리기와 재생 안내.md`) |
| 이미지 | 그림 |
| 문서 | PDF면 첫 쪽. hwp 등은 "브라우저 미리 보기 없음 — 내려받아 열기" |
| 센서 | 앞 채널 몇 개의 파형(`GetPassWaveform`이 쓰는 표준화본) |
| 포즈 | 관절 그림 한 프레임 |
| 깊이 원본 | 재생 불가 안내. 같은 녹화의 컬러 영상으로 확인 |

**올리기 창.** 파일 · 작업 · 패스(작업의 패스 또는 공용) · 장비 · 시간 0의 시각.

- 파일을 고르면 `ListUploadFormats`의 확장자로 종류를 짐작해 보여 주고, 시간 자료면 시각 칸을 필수로 표시하고, 올린 뒤 돌 후처리 단계를 보여 준다. 종류는 서버가 내용으로 최종 판별한다.
- `FormData`에 `metadata`를 `file`보다 먼저 넣는다.
- 작업 없이 올리면 "작업 미지정"으로 보이고, 상세의 [작업에 붙이기]로 나중에 붙인다.
- 응답의 `warnings`는 그대로 보여 준다. 같은 내용의 에셋이 있으면 그 번호도 온다(§5.4).
- 센서 · 포즈의 프로필은 고르는 칸이 없다 — 서버가 CSV · xlsx 머리행의 시간 열로 정한다(`절대시각_epoch` 패널 · `bag_time_ns` IMU · `구간초` 회전수 · `t_abs` 통합 신호 · 스켈레톤). 넷 다 없으면 종류 없이 등록만 되고 후처리가 안 걸린다(응답 `asset.kind`가 비고 `runId`가 없음). 그때 화면은 "시간 열을 못 찾아 등록만 됨 — 지원하는 열: 절대시각_epoch · bag_time_ns · 구간초 · t_abs"를 보인다. 새 장비 형식은 사람이 고르게 하지 않고 서버에 프로필을 더한다(`democell/normalize.go` `timeColumns`).

### 5.4 중복 확인

**구현됨(2026-10-19, 이관 20).** 아래 제안과 다른 점: 결정 값은 글자 대신 enum `DuplicateDecision`(`MERGED` · `KEEP_SEPARATE`), `DuplicateMember`는 `DuplicateGroup.members`(7)로 넣었고 참조 수 `MergeCounts`도 지금 함께 만들었다(§5.5가 같은 것을 쓴다). 판정은 `entities.MergeCheck` 한 곳. 결정 `merged`를 쓰는 것은 §5.5(`MergeAssets`)라 아직 없다.

운영 DB(2026-10-14) 기준 sha256이 같은 묶음이 416개, 남는 사본이 17,362개다. 그런데 **394개 묶음은 사본마다 기록 시각(`recorded_at`)이 다르다** — devseed가 예시 공사(EX001~EX006)를 만들며 같은 파일을 시각만 옮겨 복사한 것이다. 내용이 같아도 시간 뜻이 다르면 다른 에셋이므로 합치면 안 된다.

시각이 같은 나머지 22묶음도 대부분 합치면 안 된다.

| 예(운영 DB) | 사본 | 왜 같은 에셋이 아닌가 |
|---|---|---|
| `paint_inspection_report_v1.1_p2_Maker.png` 1265 · `…_p46_Maker.png` 1548 | 2 | 같은 서명 그림을 **다른 PDF(1263, 102)의 다른 쪽**에서 잘라 냄 — 만든 경위가 다르다 |
| `2호기.pdf` 102 · 4255 · 6011 · 7578 · 14158 | 5 | **사본마다 성적서 세트가 6개씩** 있다(예시 공사마다 따로 매칭). 합치면 세트가 30개로 겹친다 |
| `용접종류 및 특징.hwp` 1108 · 1130 | 2 | 같은 원본(`source_path` 같음)이 작업 197 · 208에 따로 들어온 것 — **합쳐도 된다** |

**합칠 수 있는 중복** = 다음이 모두 맞을 때.

- sha256 · `kind` · `recorded_at`이 같다.
- 장비가 같거나 한쪽이 비어 있다.
- 만든 경위가 같다: 둘 다 원본이거나, 부모 · `operation` · `parameters`가 같다.
- 성적서 세트(`report_set.source_asset_id`)와 파생(자식)이 **둘 이상의 사본에 있지 않다**. 한쪽에만 있으면 그쪽을 남기면 된다.

```proto
message ListDuplicateAssetsRequest {
  ...
  bool include_time_shifted = 3; // 기본 false: 기록 시각이 서로 다른 묶음은 뺀다
}
message DuplicateGroup {
  ...
  bool mergeable = 3;
  string reason = 4;             // 못 합치면 이유: "기록 시각이 다름", "만든 경위가 다름", "사본마다 성적서 세트가 있음"
}
```

판정은 서버가 한다(화면이 같은 조건을 따로 들고 있지 않게). 비교 화면에 필요한 칸(붙은 작업 · 클립 · 파생 · 성적서 세트 수)은 `DuplicateGroup.assets`의 `Asset`에 없으므로, 묶음 안 에셋마다 `MergeAssets(dry_run)`과 같은 집계를 담는 `DuplicateMember { Asset asset; MergeCounts refs; repeated int64 job_ids; }`로 주는 것을 제안한다.

**비교 화면**(화면안 에셋 탭 [중복 보기]):

- 왼쪽: 묶음 목록(sha256 · 파일 · 사본 수 · 판정 "합칠 수 있음/못 합침"). 기본은 시각이 다른 사본을 뺀 목록, 체크하면 `include_time_shifted`.
- 오른쪽: 사본을 **열**로 놓고 **줄**로 비교한다. 사본끼리 다른 칸은 강조한다.
  - 맨 위 줄은 **미리 보기**(§4와 같은 것). sha256이 같으면 바이트까지 같은 파일이라 내용 차이는 없다 — 미리 보기는 "무엇인지" 눈으로 확인하는 용도이고, 판정은 아래 줄들로 한다.
  - 공통 줄: 파일 이름 · 종류 · 크기 · 기록 시각 · 장비 · 원본 위치 · 만든 경위 · 붙은 작업 · 클립 · 파생 · 성적서 세트.
  - 종류별 줄: 사본들의 `Asset.display` 라벨을 합쳐 그대로 줄로 넣는다(영상이면 해상도 · 프레임 · 코덱 · 첫 프레임 시각 · 소리). 화면이 종류별 줄을 따로 정하지 않는다.
  - 미리 보기는 **하나씩**(사본 탭 · ◀ ▶로 바꿔 가며 크게)과 **나란히**를 고를 수 있다. 각 사본의 실제 파일을 `content_url`로 연다 — sha256을 믿되 눈으로도 확인할 수 있게.
- 아래: 판정과 이유, 그리고 정리 버튼 둘.
  - **[기준 n으로 합치기]**: "기준"으로 고른 사본(기본: 참조가 가장 많은 것, 같으면 번호가 작은 것)으로 합친다. 누르면 `MergeAssets(dry_run)`을 불러 옮겨질 수를 확인 창에 보여 주고, 확인하면 실행한다.
  - **[그대로 두기]**: 중복이 아니라고 기록한다(`ResolveDuplicateGroup`, 아래). 목록에서 빠진다. 못 합치는 묶음(예시 사본 등)도 이것으로 정리한다.
  - "정리한 묶음도 보기"를 켜면 정리한 묶음이 다시 보인다.

**정리 결정 기록과 새 사본.** 정리한 묶음에 같은 내용의 파일이 또 들어오면 다시 떠야 한다. 그래서 결정할 때 **그때의 사본 번호**를 남기고, 그 밖의 사본이 생기면 묶음을 다시 보여 준다.

```sql
-- 이관 20(제안)
CREATE TABLE tacit.asset_duplicate_decision (
  sha256           text PRIMARY KEY,
  decision         text NOT NULL CHECK (decision IN ('merged', 'keep_separate')),
  keep_asset_id    bigint REFERENCES tacit.asset ON DELETE SET NULL, -- 합친 기준(그대로 두기면 화면에서 고른 기준, 없어도 됨)
  member_asset_ids bigint[] NOT NULL,  -- 결정할 때 묶음에 있던 사본. 이 밖의 사본이 생기면 다시 뜬다
  decided_at       timestamptz NOT NULL DEFAULT now()
);
```

```proto
// 중복 묶음을 "그대로 둔다"고 기록한다(합치지 않음). 같은 sha256의 결정이 있으면 덮어쓴다.
rpc ResolveDuplicateGroup(ResolveDuplicateGroupRequest) returns (ResolveDuplicateGroupResponse);
message ResolveDuplicateGroupRequest {
  string sha256 = 1;
  repeated int64 member_asset_ids = 2; // 화면이 본 사본들 — 그사이 새 사본이 들어왔으면 FailedPrecondition(다시 보고 결정)
  int64 keep_asset_id = 3;             // 선택
}
message ResolveDuplicateGroupResponse {}

message ListDuplicateAssetsRequest { ... bool include_resolved = 4; } // 정리한 묶음도
message DuplicateGroup {
  ...
  DuplicateResolution resolution = 5;  // 정리한 적이 있으면
  repeated int64 new_asset_ids = 6;    // 결정 뒤에 들어온 사본(이것 때문에 다시 뜬 것)
}
message DuplicateResolution { string decision = 1; int64 keep_asset_id = 2; google.protobuf.Timestamp decided_at = 3; }
```

- `MergeAssets`가 성공하면 같은 표에 `merged`로 기록한다(사본 = 기준 하나).
- 기본 목록은 **결정이 없거나, 결정 뒤 새 사본이 있는 묶음**만 보인다.
- 새 사본이 다시 뜨면 화면은 그 사본에 "새로 들어옴"을 붙이고, 합친 묶음이면 **기준 번호가 이미 정해져 있어** 바로 그 기준에 합칠 수 있다.
- 올릴 때(`POST /assets`)도 결정을 본다: 같은 sha256의 결정이 있으면 `warnings`에 "합친 묶음의 기준 1108" 또는 "그대로 두기로 한 묶음"을 적고 `duplicateOf`에 기준 번호를 준다.

**올릴 때 알림.** `POST /assets` 응답에 같은 sha256 에셋이 있으면 `warnings`에 "같은 내용의 에셋 2302가 이미 있음"을 넣고, 번호를 `duplicateOf: [2302]`로도 준다. 등록은 막지 않는다(지금 규칙). 브라우저가 큰 파일의 해시를 미리 구하기 어려워 올린 뒤 알린다. 고칠 곳: `internal/delivery/files/upload.go`.

### 5.5 `MergeAssets` — 중복 합치기

**구현됨(2026-10-19).** 아래 순서 그대로, 판정은 §5.4와 같은 `entities.MergeCheck`다. 다른 점: 저장 경로(`storage_path`)는 이미 유일해서 사본의 파일은 늘 지운다. `dry_run`은 같은 트랜잭션을 끝까지 돌린 뒤 되돌리므로 수가 실제와 같다. 성공하면 결정 표에 `merged`(사본 = 기준 하나)를 남긴다.

```proto
// 같은 에셋 여럿을 하나(keep)로 합친다. 참조를 keep으로 옮기고 나머지 행·파일을 지운다(되돌릴 수 없음).
// 합칠 조건(§5.4)이 안 맞으면 FailedPrecondition.
rpc MergeAssets(MergeAssetsRequest) returns (MergeAssetsResponse);

message MergeAssetsRequest {
  int64 keep_asset_id = 1;
  repeated int64 merge_asset_ids = 2;
  bool dry_run = 3;                 // true면 바꾸지 않고 옮겨질 참조만 센다
}
message MergeAssetsResponse {
  Asset asset = 1;                  // 남은 에셋
  MergeCounts moved = 2;
  repeated int64 deleted_asset_ids = 3;
  repeated string warnings = 4;
}
message MergeCounts {
  int32 attachments = 1;            // job_asset
  int32 clips = 2;
  int32 children = 3;               // 파생 자식의 parent_asset_id
  int32 report_refs = 4;            // report_set · document
  int32 tool_runs = 5;
}
```

한 트랜잭션에서 이 순서로 한다.

1. 합칠 조건을 검사한다(§5.4와 같은 판정).
2. **첨부를 keep으로 옮긴다**(`tacit.job_asset`). 같은 작업에 둘 다 붙어 있으면 keep 쪽을 남기고, 패스가 다르면 keep 쪽 값을 따르고 `warnings`에 적는다.
3. **클립을 옮긴다**(`tacit.clip.source_asset_id`). 클립은 그 작업에 첨부된 에셋만 가리킬 수 있어(외래 키) 2번 다음이어야 한다.
4. 나머지 참조를 옮긴다: `tacit.asset.parent_asset_id`(파생 자식), `doc.report_set.source_asset_id` · `split_asset_id`, `doc.document.source_asset_id` · `asset_id`, `tacit.tool_run.asset_id`.
5. 사본 행을 지운다(`asset_provenance`는 따라 지워진다). 파일은 다른 행이 같은 저장 경로를 쓰지 않을 때만 지운다.

화면 흐름: 에셋 탭 [중복 보기] → 묶음 고르기 → 남길 에셋 고르기(기본: 참조가 가장 많은 것) → `dry_run`으로 "첨부 3 · 클립 2 · 파생 1이 옮겨집니다" → 확인 → 합치기.

**합친 기록(선택).** 지운 번호 → keep 번호를 남기는 표(`tacit.asset_merge`)를 두면 밖에 적어 둔 옛 번호를 찾을 수 있다. 옛 번호를 저장하는 외부 시스템이 아직 없어 지금은 두지 않는다 — 이것만 이관이 필요하다.

### 5.8 성적서 PDF 파생의 부모 바로잡기 — 원본 → 묶음 → 문서 → OCR · 그림

**구현됨(2026-10-19, 이관 21).** 규칙은 DB 함수 `tacit.relink_pdf_derivatives(원본)` 하나에 두고 이관과 적재(`SplitDocuments` 끝)가 같이 부른다. 다시 추출 · 다시 매핑의 지우기(`clear`)는 먼저 원본 아래로 평평하게 되돌린 뒤 지우고, 끝에 다시 잇는다. `DerivedAssetIDs`는 후손 전체(깊은 것부터), 후처리의 "이미 추출했나"도 후손으로 본다. 음성 추출 · 표준화의 `FindDerived`는 바로 아래 자식 그대로(손자를 보면 파생 영상의 음성을 원본 것으로 잘못 찾는다). 운영 사본에서: 부모를 바꾼 파생 1,166개(위 표와 같음), 수집 현황 18,218건 그대로, 1호기.pdf 다시 매핑이 같은 모양(묶음 6 · 문서 29 · OCR 35 · 그림 147)으로 다시 이어짐.

**알게 된 것(이번 변경과 무관, 예전부터).** 예시 공사(EX002~EX006)의 세트 71개가 복사본 원본을 가리키면서 잘라 낸 PDF는 원래 원본(101 등)의 것을 같이 쓴다. 그래서 원래 원본을 다시 매핑하면 그 PDF를 지우지 못해 멈춘다. 잘라 낸 PDF가 작업에 첨부돼 있어도 멈춘다. 다시 매핑 전에 매칭 · 첨부를 푸는 순서가 필요하다.

**지금(운영 DB 2026-10-15).** 원본 성적서 PDF에서 만든 파생이 모두 원본 바로 아래에 같은 높이로 붙어 있다. 원본 101 `1호기.pdf`(45쪽)의 자식 217개는 이렇다.

```
101 1호기.pdf
 ├ pdf_split 35        묶음 PDF 2302(p17~23)와 문서별 PDF 19690(p17 fitup) … 가 나란히
 ├ text_extraction 35  OCR JSON(쪽마다)
 └ image_crop 147      잘라 낸 그림(쪽 · 칸마다)
```

그래서 에셋 탭에서 묶음 PDF 2302를 펼쳐 그 문서들과 OCR · 그림으로 내려갈 수 없다(2302의 `child_count`는 0). 작업 필터에서는 첨부된 묶음 PDF만 보이고 끝난다 — OCR 199 · 그림 837은 어느 작업에도 첨부돼 있지 않다. 성적서 RPC(`GetReportSet`)도 문서별 PDF(`Section.asset_id`)까지만 준다.

**바꿀 규칙.** 파생의 부모 = **그 쪽 범위를 담는 가장 작은 PDF 파생**(문서별 PDF > 묶음 PDF > 원본). 쪽 하나의 바이트는 원본 · 묶음 · 문서별 PDF에서 같으므로 "무엇으로 만들었나"가 틀어지지 않는다.

```
101 1호기.pdf
 └ 2302 1호기_p17-23.pdf                  (묶음, 작업에 첨부)
    ├ 19690 1호기_p17-17_fitup.pdf        (문서)
    │  ├ 1320 fitup_insp_report_v1_p17.json   (OCR)
    │  └ 1321 · 1322 · 1323 잘라 낸 그림
    ├ 19691 1호기_p18-18_welding.pdf …
    └ 19694 1호기_p21-23_ndt.pdf
       ├ 1409 …_p21.json · 1341 …_p23.json
       └ 잘라 낸 그림
```

쪽 범위는 `Provenance.parameters`에서 읽는다. 키가 만든 방법마다 다르다.

| 만든 방법 | 쪽 범위 |
|---|---|
| `pdf_split` | `page_start` ~ `page_end`. `document_id`가 있으면 문서별, 없으면 묶음 |
| `text_extraction` | `start_page` ~ `start_page + num_pages − 1` |
| `image_crop` | `page` |

**운영 DB에서 맞춰 본 결과(2026-10-15)** — 담는 것이 하나로 정해진다(둘 이상인 경우 없음).

| 파생 | 담는 문서별 PDF가 하나 | 없음 → |
|---|---|---|
| OCR JSON 199 | 195 | 4는 묶음 PDF가 담으면 묶음, 아니면 원본에 그대로 |
| 잘라 낸 그림 837 | 819 | 18은 위와 같이 |

| 파생 | 담는 묶음 PDF가 하나 | 없음 → |
|---|---|---|
| 문서별 PDF 529 | 152 | 377은 원본에 그대로(그 쪽을 담은 묶음이 없는 원본) |

깊이는 원본까지 넷이 된다(지금은 둘).

**고칠 곳**

### 5.9 `ListJobFilters` 개수 — 목록 행마다 세지 않게

| 합칠 때 파생끼리도 합치나(사본마다 음성 추출이 따로 있으면 keep 아래 같은 파생이 둘) | 자동으로 합치지 않는다. 다음 중복 묶음으로 보이게 둔다 |
| 합친 기록 표(`asset_merge`, 지운 번호 → 남긴 번호)를 둘까 | 따로 두지 않는다. 정리 결정 표(`asset_duplicate_decision`)에 sha256 단위로 기준과 그때의 사본 번호가 남는다 |
| 합친 묶음에 같은 파일이 또 올라오면 자동으로 기준에 합칠까 | 자동으로 하지 않는다. 다시 중복으로 띄우고 사람이 한 번 누른다 |
| 예시 사본 394묶음 | 합치지 않는다. 기본 목록에서만 뺀다(`include_time_shifted`로 볼 수 있음) |
| 에셋 → 작업 찾기에 부모의 첨부도 포함할까 | 그 에셋이 직접 붙은 작업만(§5.2, 구현됨) |
| 사파리에서 ms 입력 | 화면 쪽 문제 — 지원 브라우저를 정할 때 본다. 크롬 · 엣지만이면 할 일 없음 |
| 둘이 같은 칸을 동시에 고치면 | 지금은 나중 저장이 이긴다. 문제가 되면 `updated_at` · `expected_updated_at`으로 막는다 |
| 그만둔 작업자 · 안 쓰는 장비 숨기기 | `inactive`(숨김)로 숨긴다(§5.10, 구현됨) |
| 작업자 이름이 같은 사람 · 추가 정보 | 사번(`employee_no`, 유일)과 비고(`description`)를 둔다(§5.10, 구현됨) |

## 7. 진행 순서

1. 서버: §5.1 · §5.2 · §5.3 · §5.7 · §5.9 (작음, 함께) → 운영 적용 → proto 전달.
2. 프론트: 공사 탭(검색 포함) → 작업자 · 장비 탭(서버 추가 없음, 지금 바로 만들 수 있다) → 작업 탭(이력 조회 표 재사용) → 에셋 탭(목록 · 상세 · 올리기).
3. 서버: §5.4(이관 20 · `ResolveDuplicateGroup` · 목록 판정) → §5.5(`dry_run`부터) → 프론트: 중복 보기 · 비교 · 정리.
4. 서버: §5.8(이관 21 · 파이프라인 다시 잇기 · 후손 조회 · 수집 현황 조건). 중복 판정이 부모를 비교하므로 §5.4보다 먼저 해도 되고 나중에 해도 판정은 같다. 이관 전후로 수집 현황 수와 성적서 다시 추출(`-reextract`) 한 번을 확인한다.

## 8. 작업자 탭

| 화면 동작 | RPC | 비고 |
|---|---|---|
| 목록 | `ListJobFilters`의 `workers`(다른 탭과 같이 씀, §1 "부르는 수") | 이름 · 사번 · 종류(명장 · 일반 · 로봇 · 모름) · 작업 수 |
| 작업 수 | `worker_job_counts`(§5.9) | 그 전에는 `ListJobs(worker_id, page_size=1)`의 `total_count`를 작업자마다 한 번 |
| 검색 | 없음(화면에서 거름) | 검색 칸(이름 · 사번) + 종류 고르기(전체 · 명장 · 일반 · 로봇 · 모름) |
| 새 작업자 | `CreateWorker` | 이름 필수 · 종류 · 사번 · 비고 |
| 고치기 | `UpdateWorker` | 바뀐 칸만 `update_mask`(`worker_name` · `worker_type` · `employee_no` · `description` · `inactive`) |
| 맡은 작업 | `ListJobs(worker_id)` | 작업 표를 그대로 쓴다. 행을 누르면 작업 탭의 그 작업으로 간다 |
| 지우기 | `DeleteWorker` | 맡은 작업이 있으면 막힘 |

화면 규칙

- **종류는 넷이다** — 명장(`MASTER`) · 일반(`GENERAL`) · 로봇(`ROBOT`) · 모름(`UNSPECIFIED`). "모름"으로 바꿀 때는 `update_mask`에 `worker_type`을 넣고 `UNSPECIFIED`를 보낸다. 비교 화면의 "명장만"(`ListJobs.worker_type = MASTER`)이 이 값을 쓰므로, 상세에 "파형 비교의 명장 목록에 들어감/빠짐"을 적어 준다.
- 이름을 고치면 그 작업자의 모든 작업에 바뀐 이름이 보인다(작업은 번호로 가리킨다) — 확인 문구를 띄운다.
- 지우기는 작업 수가 0일 때만 버튼을 켠다. 0이 아니면 "작업 n건을 맡음 — 작업 탭에서 작업자를 바꾸거나 지운 뒤"를 보인다. 서버도 `FailedPrecondition`으로 막는다.
- 작업자 없는 작업(2026-10-15 기준 2건)은 이 탭에 안 보인다. `ListJobs`에 "작업자 미지정" 필터는 없다 — 작업 표의 작업자 칸이 비어 있는 것으로 본다.

## 9. 장비 탭

| 화면 동작 | RPC | 비고 |
|---|---|---|
| 목록 | `ListJobFilters`의 `equipment`(다른 탭과 같이 씀) | 장비 코드 · 이름 · 라인 · 쓰인 작업 수 |
| 쓰인 작업 수 | `equipment_job_counts`(§5.9) | "그 장비의 에셋이 첨부된 작업" 수. 그 전에는 `ListJobs(equipment_id, page_size=1)`의 `total_count` |
| 검색 | 없음(화면에서 거름) | 검색 칸(코드 · 이름 · 라인) + 라인 고르기 |
| 새 장비 | `CreateEquipment` | 이름 필수 · 라인 · 코드. 코드가 겹치면 `AlreadyExists`를 코드 칸 아래에 |
| 고치기 | `UpdateEquipment` | 바뀐 칸만 `update_mask`(`equipment_name` · `line_name` · `equipment_code`) |
| 쓰인 작업 | `ListJobs(equipment_id)` | 작업 표를 그대로 쓴다 |
| 기록한 에셋 | **`ListAssets(equipment_id)`(§5.3)** | 에셋 탭 목록과 같은 표, 50개씩. 행을 누르면 에셋 탭의 그 에셋으로 간다 |
| 지우기 | `DeleteEquipment` | 기록한 에셋이 있으면 막힘 |

화면 규칙

- **장비 코드는 적재기가 장비를 찾는 열쇠다.** 적재기(`ingest_repository_impl.go`)는 코드로 장비를 찾고, 없으면 그 코드로 장비를 새로 만든다. 그래서 코드를 바꾸면 다음 적재 때 옛 코드의 장비가 새로 생겨 같은 장비가 둘이 된다. 코드 칸은 읽기 전용으로 보이고 [코드 바꾸기]를 눌러야 열리게 하며, "적재 설정의 코드도 함께 바꿔야 함"을 확인받는다.
- 코드는 비워도 된다(손으로만 고르는 장비). 비우면 적재기가 이 장비를 못 찾는다.
- 코드는 공백을 빼고 대문자로 보낸다(지금 값이 모두 `DEMO-ACTIONCAM`처럼 대문자 · 하이픈).
- 지우기 전 확인: `equipment_asset_counts`(§5.9)가 0일 때만 버튼을 켠다(§5.9 전에는 `ListAssets(equipment_id, page_size=1)`이 비어 있을 때). 운영 DB의 장비 4대는 모두 에셋이 있어(968~6,516건) 지금은 못 지운다. §5.3 전에는 버튼을 켜 두고 서버의 `FailedPrecondition` 문구를 그대로 보인다.
- 에셋 수는 `equipment_asset_counts`(§5.9)로 목록에 함께 보인다. 그 전에는 주는 RPC가 없다(`ListAssets`에 `total_count` 없음).
