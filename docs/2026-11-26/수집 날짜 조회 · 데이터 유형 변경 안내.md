## 1. 날짜 조회 — `from` · `to`

```proto
message ListCollectionNodesRequest {
  ...
  reserved 2, 3; // 옛 start_offset_ns · end_offset_ns — 지웠습니다
  google.protobuf.Timestamp from = 7; // 새로 — [from, to). 비우면 처음 / 끝까지
  google.protobuf.Timestamp to = 8;
}
message GetCollectionSummaryRequest {
  CollectionPath parent = 1;
  int64 worker_id = 2;
  google.protobuf.Timestamp from = 3; // 새로 — ListCollectionNodes와 같은 값을 주세요
  google.protobuf.Timestamp to = 4;
}
```

- 화면의 일자 · 시작 · 종료를 그대로 `from` · `to`로 보내 주세요(한국 시각 9/16 00:00 ~ 9/17 00:00이면 `2026-09-15T15:00:00Z` ~ `2026-09-16T15:00:00Z`). 트리와 카드에 **같은 값**을 주면 둘이 같은 작업을 셉니다.
- `from` ≥ `to`면 `InvalidArgument`입니다.
- **나오는 것**: 용접 구간이 조회 구간과 조금이라도 겹치는 작업만. 위 단계(공사 · 품목)는 그런 작업이 있을 때만 나옵니다. 작업에 붙지 않은 파일("미지정")은 구간을 주면 나오지 않습니다.
- **카드 값**
  - 작업 수 · 작업 시간 · 용접 시간 · 커버리지: 겹치는 작업만, 시간은 조회 구간으로 잘라서 셉니다. 자정을 넘긴 패스는 날짜마다 나뉩니다.
  - 파일 수 · 용량 · 임베딩 · 코멘트: 겹치는 작업의 것 **전부**(파일 기록 시각은 보지 않음).
- **옛 `start_offset_ns` · `end_offset_ns`는 지웠습니다(깨지는 변경).** 보내도 무시되어 구간 없이 조회됩니다 — `from` · `to`로 바꿔 주세요.

### 카드 파일 수와 `ListAssetCounts`가 다를 수 있습니다

`ListAssetCounts`(날짜 × 종류)는 그대로입니다 — "그 날 무엇이 들어왔나"를 파일 시각(기록 또는 받은 시각)으로 셉니다. 카드는 "그 기간 작업의 파일"이라 둘이 다를 수 있습니다.

예(DEMO, 9/16): 카드 326개 · `ListAssetCounts` 합 286개. 9/16에 시작한 작업의 9/17 아침 패스 파일은 카드에만, 작업에 안 붙은 파일은 그래프에만 들어갑니다. 구간 없이 부르면 둘은 같습니다.

## 2. KPI 카드 — 네 묶음

모두 `GetCollectionSummaryResponse` 한 번으로 채웁니다.

| 카드 | 크게 | 작게 |
|---|---|---|
| 수집량 | `summary.asset_count` 개 | `total_size_bytes` |
| 작업량 | `weld_duration_seconds` (용접 시간) | `job_count` 건 · `job_without_asset_count` · `work_duration_seconds` |
| 커버리지 | 종합 %, 괄호에 손실률 | 유형별 % (`data_type_coverage`, §5) |
| 임베딩 | 종합 %, 괄호에 끝난 수 / 대상 수 | 클립 · 파일 · 코멘트 각각 % (끝난 수 / 대상 수) |

- **작업량 — 추정**: 끝 시각이 없는 작업(TP129 등)은 기본 용접 시간(53분 15초)으로 넣은 값입니다. 카드에서 따로 나누지 않고, 어느 작업이 추정인지는 그 작업 막대의 `TimeRange.estimated`(점선 등)로 보여 주세요. (배포 전 안내했던 `estimated_weld_seconds`는 지웠습니다.)
- **커버리지**: §5. 예(DEMO 9/16): **92.9% (손실률 7.1%)** — 액션캠 영상 61.3% · 앞 깊이 영상 99.0% · 뒤 깊이 영상 98.9% · 앞 RGB 영상 99.0% · 뒤 RGB 영상 98.9% · 패널 시계열 100%. 목표(99%) 표시는 하지 않습니다.
- **임베딩**: 세 가지 모두 같은 꼴로. 단위(구간 · 연결 · 건)는 쓰지 않아도 됩니다.
  - 클립 `embedded_clip_count` / `clip_count`
  - 파일 `embedded_attached_asset_count` / `attached_asset_count` (작업-파일 연결 수라 한 파일이 두 작업에 붙으면 둘)
  - 코멘트 `embedded_comment_count` / `comment_count`
  - 종합 = 끝난 수 합 ÷ 대상 수 합. 대상이 0이면 "-".
- **적재 카드는 빼 주세요.** 진행 · 실패 수(`trace_running_count` · `trace_failed_count`)는 조건과 상관없는 늘 전체 값이라 카드 줄에 두면 날짜를 바꿔도 안 바뀌어 헷갈립니다. "적재 파이프라인" 탭 제목 옆 배지(예: "실패 7")로 옮겨 주세요. 옮기신 뒤 이 두 칸은 지웁니다(탭은 `ListTraces`의 `total_count`로도 셀 수 있습니다).

## 3. 트리 · 막대

```proto
message CollectionNode {
  ...
  repeated TimeRange segments = 8;
  repeated TimeWarning warnings = 9; // 새로 — 작업 노드만(§4)
}
message TimeRange {
  google.protobuf.Timestamp started_at = 1;
  google.protobuf.Timestamp ended_at = 2;
  int64 job_id = 3;   // 새로 — 작업 구간 기준 막대의 작업
  int64 pass_id = 4;  // 새로 — segment_unit PASS일 때 그 패스(패스가 없는 작업이면 0 → 칸 없음)
  bool estimated = 5; // 새로 — 끝 시각이 없어 기본 용접 시간으로 만든 막대
}
```

- 행은 공사 → 품목 → 작업입니다. **작업 아래 파일 행은 쓰지 말아 주세요** — 작업의 파일은 상세 패널에서 `ListAssets`(작업 필터)로, 작업 KPI는 `GetCollectionSummary`(그 작업을 parent로)로. 옮기신 뒤 서버에서 파일 노드를 지웁니다.
- 막대(작업 구간 기준 `basis` WORK)
  - 어느 단계 행이든 그 아래 **작업마다 하나**(`segment_unit` JOB) 또는 **패스마다 하나**(PASS). 합치지 않습니다 — 동시에 한 작업은 막대가 겹칩니다.
  - 막대 = 용접 구간이라 카드의 용접 시간과 같은 길이입니다. 패스 시각이 비면 그 패스의 센서 파일 구간으로 채운 값입니다.
  - **조회 구간으로 자르지 않습니다.** 구간 밖으로 이어지는 막대는 축 끝에서 잘라 그리고 "→" 같은 표시를 붙여 주세요(예: 작업 02 · 9/16은 9/17 09:11까지).
  - 누르면 `job_id`(· `pass_id`)로 그 작업 · 패스 상세로 가면 됩니다.
  - `estimated`면 점선 · 빗금 등 실제 시각과 다르게 그려 주세요.
- 수집 구간 기준(`basis` COLLECTION) 막대는 지금처럼 파일 기록 구간(합침, 번호 없음)입니다.
- 작업 노드 `has_children`: 파일이 있는 작업만 true.

## 5. 데이터 유형 · 공사 필수 · 커버리지

### 데이터 유형이란

공사가 "잘 모였나" 확인하려는 단위입니다 — 앞 깊이 영상과 뒤 깊이 영상은 같은 기종 · 같은 형식이지만 서로 대신할 수 없으니 다른 유형입니다.
**장비와 묶지 않습니다**(카메라를 바꿔도 "앞 깊이 영상"). 장비는 파일의 출처(`Asset.equipment_id`)로만 남습니다.

  DATA_TYPE_JUDGE_REPORT = 2;      // 작업 성적서 세트에 doc_type 문서가 있나(파일에 붙이지 않음)

  string data_type_name = 2;                  // '앞 깊이 영상'. 겹치면 안 됨

### 관리 RPC(WorkService) — 장비 관리와 같은 꼴

**관리 화면은 나중에 해도 됩니다.** 지금 먼저 필요한 것은 업로드 화면의 유형 고르기와 공사 편집의 필수 유형 고르기이고, 둘 다 `ListDataTypes`(권한 `view`)만 씁니다. 만들기 · 고치기 · 다시 맞추기는 `work.edit` 권한이고, 관리 화면이 생기기 전까지는 서버 쪽에서 RPC로 넣습니다. 유형 관리 전용 권한 · 역할 연결도 나중에 정합니다.

| RPC | 하는 일 |
|---|---|
| `ListDataTypes` | 번호 순. 숨긴 유형은 빠짐, `include_inactive`면 전부 |
| `CreateDataType` | 이름 겹치면 `AlreadyExists`, REPORT인데 `doc_type`이 없거나 TIME인데 있으면 `InvalidArgument` |
| `UpdateDataType` | `update_mask`: `data_type_name`, `judge`, `doc_type`, `match_kind`, `match_file_name`, `description`, `inactive`. **숨김도 이것으로**(`inactive` true / false). 지우는 RPC는 없습니다 |
| `RematchDataTypes` | 유형을 늘리거나 조건을 고친 뒤 파일에 다시 붙임. 기본은 미지정 파일만, `overwrite`면 이미 붙은 것도(사람이 고른 것도 바뀜). `changed_count` |

### 파일의 유형 — `Asset.data_type_id`(asset.proto 22)

- 0(칸 없음) = **미지정**. 커버리지에 들지 않습니다. 규칙에 없는 파일, 그리고 업로드 때 고르지 않은 키포인트 · 오버레이가 미지정이 됩니다 — 나중에 `UpdateAsset`으로 고르거나, 유형을 만들고 `RematchDataTypes`.
- 정해지는 순서: ① 업로드 metadata `dataTypeId` ② 안 주면 `match_kind` · `match_file_name`이 맞는 유형이 **하나뿐**일 때 서버가 붙임(없거나 여럿이면 미지정) ③ 표준화 파생은 원본 유형을 물려받음.
- 업로드: metadata에 `"dataTypeId": "3"`(선택). **키포인트 · 오버레이는 조건이 없는 유형이라 화면에서 앞 · 뒤를 꼭 고르게 해 주세요**(여러 파일을 올리면 파일마다). 없는 번호 · 숨긴 유형 · 성적서(REPORT) 유형이면 파일을 받기 전에 400입니다. 고르는 목록은 `ListDataTypes`에서 TIME 유형만.
- 고치기: `UpdateAsset` mask `data_type_id`(0 = 비움). 업로드와 같이 없는 · 숨긴 · 성적서 유형이면 `InvalidArgument`.
- 화면: 파일 상세에 유형 이름(목록에서 번호로 찾기), 미지정이면 "미지정".

### 공사 필수 — `Project.required_data_type_ids`(8)

message Project {

  repeated int64 required_data_type_ids = 8; // 비면 필수 없음(커버리지 줄 없음)

// CreateProject는 그대로 보내면 되고, UpdateProject는 update_mask에 "required_data_type_ids" — 목록을 통째로 바꿉니다.

- 배포 때: DEMO · EX = 액션캠 · 앞/뒤 깊이 · 앞/뒤 RGB · 패널(6개), TP129 = 취부 · 용접 · 치수 · 압력 · 비파괴 성적서(5개). 그 밖의 공사는 비어 있습니다.
- 화면: 공사 상세 · 편집에 필수 유형 고르기(`ListDataTypes` 목록 체크). 고치면 과거 값도 다시 계산됩니다(저장하지 않고 조회할 때 셈).

### 커버리지 — `GetCollectionSummaryResponse.data_type_coverage`(5)

```proto
message DataTypeCoverage {
  int64 data_type_id = 1;
  string data_type_name = 2;
  DataTypeJudge judge = 3;
  int64 covered_seconds = 4;  // TIME: 용접 시간 중 그 유형 파일이 기록한 시간. REPORT: 세트에 그 문서가 있는 작업의 용접 시간
  int64 expected_seconds = 5; // 그 유형이 필수인 작업들의 용접 시간
}
```

- 범위 안 공사들의 필수 유형만, 유형 번호 순으로 옵니다. 어느 공사에도 필수가 아닌 유형은 줄이 없습니다. **온 줄만 그려 주세요.**
- 종합 = `covered_seconds` 합 ÷ `expected_seconds` 합, 손실률 = 100% − 종합. 유형별 % = `covered_seconds` ÷ `expected_seconds`, `expected_seconds`가 0(또는 없음)이면 "-". 줄이 하나도 없으면 카드는 "-".
- **트리 행(`CollectionNode.summary`)에는 없습니다.** 행을 고르면 그 행을 `parent`로 `GetCollectionSummary`를 불러 상세 패널에 유형별로 보여 주세요(예: DEMO 작업 199 — 액션캠 영상 79.6%).
- TP129만 보면 성적서 다섯 줄(예: 취부 · 치수 96.2%, 용접 · 압력 · 비파괴 100%).
- **지워진 칸**: `CollectionSummary.coverage`(12) · `KindCoverage`, `GetCollectionSummaryResponse.coverage_by_equipment`(4) · `KindEquipmentCoverage`. 장비별 커버리지는 없어졌습니다.
