# weld-dashboard — Cursor 에이전트로 기능을 구현하는 방식 (기존)

이 문서는 P0~P1 하네스 보완 **이전**의 기능 구현 방식을 기록한다.  
현재 방식은 [`docs/2026-11-03/Cursor_에이전트_기능구현_방식.md`](../2026-11-03/Cursor_에이전트_기능구현_방식.md)와 루트 [`AGENTS.md`](../../AGENTS.md)를 본다.

당시 구현 절차의 기준은 `.cursor/rules`와 `.cursor/skills`에 있었고, 에이전트는 그 규칙을 매 요청마다 따랐다. (검증 스크립트·`AGENTS.md`·구현 후 검수·회고는 아직 없었다.)

---

## 1. 한 줄 요약

**코드를 바로 고치지 않는다.** Ask에서 읽고 분석하고, Plan에서 작업 프롬프트를 짜고, 사용자가 확인하면 그 내용을 `docs/<날짜>/<작업>_프롬프트.md`로 저장한 뒤, Agent는 **그 마크다운만** 보고 구현한다. 구현 전에는 앱 목적(`README.md`)과 회사 Flutter 코딩 가이드라인(원격 저장소, 읽기 전용)을 맞춘다.

---

## 2. 왜 이렇게 쓰는가

| 문제 | 이 방식에서 막는 것 |
|------|---------------------|
| 채팅만 보고 범위가 커짐 | 확인된 프롬프트 파일 밖은 수정하지 않음 |
| 가이드라인·폴더 구조 무시 | 구현 전 원격 guidelines를 워킹 트리 밖에서 읽음 |
| 공정 전용 UI로 고착 | `README` 목적: 범용 멀티모달 가시화 |
| 추상화·헬퍼 남발 | 프롬프트마다 「복잡한 코드 제거 및 금지」 고정 조항 |
| 커밋이 섞이거나 자동 커밋 | 사용자 요청 시에만, 목적별로 나눠 커밋 |

결과적으로 에이전트는 “알아서 구현하는 AI”가 아니라, **문서로 고정된 작업 지시서의 실행기**에 가깝다.

---

## 3. 규칙과 스킬의 역할

### 3.1 Always-on Rules (`.cursor/rules/*.mdc`)

대화마다 자동으로 적용된다. 기능 구현과 직접 맞닿는 것은 아래 네 가지다.

| 규칙 | 역할 |
|------|------|
| `work-prompt.mdc` | 구현·수정은 Ask → Plan → 프롬프트 md → Agent 순. 확인된 문서 없으면 코드 금지 |
| `apply-guidelines.mdc` | Flutter/Dart 작업 전 원격 guidelines 읽고 배치·네이밍 맞춤 |
| `dashboard-purpose.mdc` | 화면·데이터 표시 전에 `README` 목적 확인. 공정 전용 구조로 고정하지 않음 |
| `git-commit-push.mdc` | 커밋·푸시는 요청 있을 때만. 목적별 커밋. guidelines는 워킹 트리에 두지 않음 |

문서 변환(PPT/PDF 등)은 `document-export.mdc`가 담당하며, **기능 코드 구현 흐름과는 별 트랙**이다.

### 3.2 Skills (`.cursor/skills/*/SKILL.md`)

규칙이 “언제 따를지”를 걸고, 스킬이 “어떻게 할지”의 상세 절차·템플릿을 담는다.

| 스킬 | 기능 구현에서의 위치 |
|------|----------------------|
| `work-prompt` | 구현·수정의 **본 절차** (모드 순서, 프롬프트 템플릿, 저장 경로) |
| `apply-guidelines` | 구현 직전 **아키텍처·네이밍·폴더** 기준 읽기 |
| `git-commit-push` | 구현 **이후** 올리기 요청 시 |
| `document-export` | 매뉴얼·발표자료. 기능 구현 요청에는 쓰지 않음 |

에이전트는 “구현해줘 / 수정해줘 / 추가해줘 / 고쳐줘”처럼 **코드 변경이 목적**이면 `work-prompt`를 연다. “프롬프트만 작성”이면 마크다운까지 쓰고 구현은 하지 않는다. 설명·질문·PRD만이면 이 스킬을 적용하지 않는다.

## 4. 기능 구현의 표준 흐름

단계를 건너뛰지 않는다. 확인된 계획과 프롬프트 마크다운이 없으면 제품 코드(`lib/**` 등)를 고치지 않는다.

```text
사용자 요청 (구현·수정)
        │
        ▼
┌───────────────────┐
│ 1. Ask — 분석     │  읽기만. 파일 생성·수정 없음
│    대상·동작·원인 │  → 프롬프트의 「먼저 읽을 것」「현재 상태」초안
└─────────┬─────────┘
          │ Plan 모드 전환 요청
          ▼
┌───────────────────┐
│ 2. Plan — 계획    │  작업 프롬프트 전체 작성
│    사용자 확인    │  해석이 갈리면 가정 금지 → 확인 질문
└─────────┬─────────┘
          │ 사용자 확인
          ▼
┌───────────────────┐
│ 3. Agent — 저장   │  docs/<YYYY-MM-DD>/<작업이름>_프롬프트.md
│    (구현 전)      │  Plan은 파일 쓰기가 제한되므로 저장은 Agent
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 4. Agent — 구현   │  저장한 md만 따른다. 문서에 없는 정리·개선 금지
│    + guidelines   │  README 목적 + apply-guidelines 절차
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 5. (선택) 커밋·푸시│  사용자 요청 시에만 git-commit-push
└───────────────────┘
```

### 4.1 Ask — 분석

- **읽기만** 한다. 파일을 만들거나 고치지 않는다.
- 대상 파일, 현재 동작, 원인, 관련 계약·화면안을 확인한다.
- 작업 프롬프트의 **분석 절**(먼저 읽을 것, 현재 상태)만 채운다.
- Ask에서는 모드 전환을 직접 할 수 없으므로, 분석이 끝나면 사용자에게 **Plan 모드로 바꿔 달라**고 요청한다.

### 4.2 Plan — 계획

- Ask에서 모은 사실로 **작업 프롬프트 전체**를 계획으로 쓴다.
- 반드시 「복잡한 코드 제거 및 금지」 고정 조항을 넣는다.
- 사용자 확인 전에는 구현하지 않고, 프롬프트 파일도 만들지 않는다.
- 애매하면 계획에 가정을 몰래 넣지 않고 **확인 질문**으로 남긴다.

### 4.3 마크다운 저장

- 사용자가 계획을 확인한 **그날**의 날짜로 저장한다.
- 경로: `docs/<YYYY-MM-DD>/<작업이름>_프롬프트.md`
- 파일 이름은 공백 없이 작업 내용이 보이게 한다.  
  예: `docs/2026-11-03/대기열표시_웹캠STT대상_프롬프트.md`
- 채팅의 계획과 파일이 다르면 **파일을 따른다.**

### 4.4 Agent — 구현

- 저장한 마크다운에 적힌 **파일·동작만** 수정한다.
- 문서가 없으면 구현하지 않고 Plan으로 되돌린다.
- 문서에 없는 리팩터, 이름 정리, 스타일 통일은 끼워 넣지 않는다.
- Agent에 “바로 구현해줘”가 들어와도, 확인된 계획이 없으면 코드를 고치지 않고 Plan 전환을 요청한다.

### 4.5 “프롬프트만”

“프롬프트만”, “프롬프트 작성만”이면 템플릿으로 md까지 만들고 **5번(구현)은 하지 않는다.**

---

## 5. 작업 프롬프트 문서의 구성

Plan과 저장 파일은 같은 템플릿을 쓴다. (출처: 당시 `.cursor/skills/work-prompt/SKILL.md`)

```markdown
# <작업 이름>

## 목표
<한 단락. 사용자가 얻게 되는 동작>

## 먼저 읽을 것
1. `README.md` 목적 절
2. `.cursor/skills/apply-guidelines/SKILL.md` (가이드라인은 워킹 트리 밖에서 읽기만)
3. <대상 파일 경로>
4. <계약·화면안 경로. 없으면 "없음">

## 현재 상태
- <파일 경로>: <지금 동작. 읽은 사실만>

## 바꿀 것
1. <구체적인 요구사항>

## 유지할 것
- <바꾸면 안 되는 동작·파일·호출 흐름>

## 이번 작업에서 만들지 않음
- <범위 밖 항목>

## 복잡한 코드 제거 및 금지
- 한 화면·한 동작을 위해 새 추상 계층, 전략, 팩토리, 제네릭 헬퍼를 만들지 않는다.
- 같은 역할의 위젯, ViewModel, UseCase, 화면 흐름이 있으면 그것을 쓴다.
- 이번 변경으로 쓰이지 않게 된 분기, 플래그, 래퍼, 죽은 코드는 제거한다.
- 조건 중첩과 모드 플래그 조합으로 경우를 늘리지 않는다.
- 호출을 한 겹 감싸기 위한 파일은 만들지 않는다. 파일 분리는 책임이 분명할 때만 한다.
- 새 상태관리, 새 디자인 시스템, 카드 UI를 도입하지 않는다.
- 프롬프트 범위 밖의 리팩터, 이름 정리, 스타일 통일을 끼워 넣지 않는다.

## 완료 확인
- <확인할 동작>
```

실무에서는 「바꿀 것」을 A/B로 나누거나, 문구 규칙·가드를 세부 bullet으로 적는 경우가 많다. `docs/` 아래 `*_프롬프트.md`가 그 기록이다.

## 6. 구현 시 에이전트가 따르는 제품·코드 기준

프롬프트 저장 후 실제 코딩에 들어가면, work-prompt만으로 끝내지 않고 아래를 **항상** 함께 본다.

### 6.1 앱 목적 (`README.md` + `dashboard-purpose`)

- weld-dashboard는 **공정에 묶이지 않는** 멀티모달 수집 대시보드다.
- 시계열·영상·음성·품질을 **같은 작업 시각** 기준으로 보여 주고, 다른 수집에도 같은 방식으로 확장한다.
- 앱이 맡는 일은 **수집값의 가시화**다. 수집값을 숨기거나, 특정 공정 전용 이름·화면 구조로 고정하지 않는다.

### 6.2 코딩 가이드라인 (`apply-guidelines`)

1. 워킹 트리 **밖** 임시 디렉터리에 `https://github.com/geosoft-co-kr/guidelines.git`를 `--depth 1`로 클론한다.
2. 필요한 `.md`를 읽는다. 새 페이지·위젯·기능이면 기본 Intro, Flutter Intro, 폴더 구조 문서는 포함한다.
3. 이름·경로·계층 경계를 그에 맞춘다.
4. 끝나면 임시 클론을 삭제한다.
5. guidelines는 **읽기만**. weld-dashboard에 클론·복사·커밋하지 않는다. 사용자에게 “가이드라인 확인할까요?”라고 묻지 않는다.

아키텍처 요약 (`lib/src/`):

- **domain** → 엔티티, 저장소 인터페이스, 유스케이스 (Flutter·gRPC 의존 없음)
- **data** → 저장소 구현, DTO, 데이터소스 (`toDomain()`). View/ViewModel에서 import하지 않음
- **presentation** → View, ViewModel, Coordinator. ViewModel은 **유스케이스만** 호출. 내비게이션은 Coordinator

기능 폴더 예:

```text
lib/src/presentation/features/<feature>/
  <feature>_screen.dart
  <feature>_view_model.dart
  <feature>_coordinator.dart
```

공통 위젯은 `lib/src/presentation/core/widgets/`, 앱 내비는 `app_coordinator.dart`.

### 6.3 완료 판단

에이전트는 프롬프트의 **완료 확인** 항목과 맞는지 본다. 분석·테스트가 항목에 있으면 그에 맞춘다. 범위 밖 개선은 하지 않는다.

## 7. 구현 이후: 커밋·푸시

기능 구현과 커밋은 분리된다. 사용자가 “커밋”, “푸시”, “커밋푸시”, “올려줘” 등을 **명시했을 때만** `git-commit-push`를 따른다.

- diff를 읽고 **파일 개수가 아니라 목적**으로 나눈다. 목적이 하나면 커밋은 하나.
- 한 동작의 domain / data / presentation / test / DI는 같은 커밋에 넣는다.
- 메시지: 한국어 1–2문장, **이유** 중심. HEREDOC 사용.
- `.env`, 비밀, 가이드라인 클론, 빌드 산출물은 커밋하지 않는다. 올리지 않을 파일은 워킹 트리에서 되돌려 `git status`에 남기지 않는다.
- 강제 푸시·`--no-verify`·대화형 rebase는 쓰지 않는다.

## 8. 기능 구현과 다른 Cursor 사용 트랙

같은 레포에서 에이전트를 쓰되, **기능 구현 파이프와 섞지 않는** 흐름이 있다.

| 요청 종류 | 절차 |
|-----------|------|
| PRD / 상세기획 | 사용자 규칙의 템플릿. work-prompt 구현 파이프와 별개 |
| PPT·PDF·DOCX·매뉴얼 | `document-export`: 관객 확인 → md 원본 → 검수 스냅샷 → 변환 |
| 단순 설명·질문 | 분석·설명만. 코드·프롬프트 파일 불필요하면 만들지 않음 |

---

## 9. 사용자·에이전트 역할 분담

| 주체 | 하는 일 |
|------|---------|
| 사용자 | 요구 제시, Ask/Plan/Agent 모드 전환 협조, Plan 확인, (선택) 커밋·푸시 요청, 완료 확인 검수 |
| 에이전트 (Ask) | 코드베이스·계약 읽기, 현재 상태 사실 정리 |
| 에이전트 (Plan) | 범위·유지·비범위·금지 조항이 들어간 작업 프롬프트 초안 |
| 에이전트 (Agent) | 확인된 프롬프트 md 저장 → guidelines·README 준수 구현 → (요청 시) 목적별 커밋·푸시 |

해석이 갈리는 요구는 에이전트가 임의로 채우지 않는다. Plan 단계에서 질문을 남기고, 확인된 내용만 문서에 넣는다.

## 10. 실제 산출물 위치

| 산출물 | 위치 |
|--------|------|
| 작업 지시서 (구현 근거) | `docs/<YYYY-MM-DD>/<작업>_프롬프트.md` |
| 에이전트 절차 | `.cursor/skills/work-prompt/SKILL.md` 등 |
| always-on 규칙 | `.cursor/rules/*.mdc` |
| 앱 목적 | `README.md` 상단 |
| 코딩 기준 (외부) | `geosoft-co-kr/guidelines` (워킹 트리 밖 임시 클론만) |

날짜별 `docs/` 폴더에 쌓인 `*_프롬프트.md`가, 그날 에이전트가 **무엇을 근거로 코드를 바꿨는지**의 감사 가능한 기록이다.

## 11. 체크리스트 (새 기능을 맡길 때)

1. 요청이 코드 변경인가? → `work-prompt` 적용.
2. Ask에서 대상·현재 상태만 정리했는가? (쓰기 금지)
3. Plan에서 목표·바꿀 것·유지·비범위·금지·완료 확인이 있는가?
4. 사용자가 Plan을 확인했는가?
5. `docs/<오늘>/<이름>_프롬프트.md`를 저장했는가?
6. 구현 전 README 목적 + guidelines(임시 클론)를 읽었는가?
7. 구현이 그 md의 「바꿀 것」만 건드렸는가?
8. 커밋은 사용자가 요청했을 때만, 목적별로 나눴는가?

이 여덟이 맞으면, **당시** 레포에서 기대하던 Cursor 에이전트 기능 구현 방식과 같다.
