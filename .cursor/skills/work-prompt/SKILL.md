# 구현·수정 작업 프롬프트

구현·수정은 Ask 분석, Plan 계획, Agent 구현 순서로만 진행한다. 단계를 건너뛰지 않는다. 확인된 계획이 없으면 코드를 고치지 않는다.

`README.md` 목적과 `.cursor/skills/apply-guidelines/SKILL.md`는 기존 규칙대로 구현 전에 따른다. 이 스킬은 그 절차를 대체하지 않는다.

## 적용

적용:

- 화면, 위젯, 기능, 버그, 연동, 리팩터를 만들거나 고치라는 요청
- 구현해줘, 수정해줘, 추가해줘, 고쳐줘처럼 코드 변경이 목적인 요청

적용하지 않음:

- "프롬프트만", "프롬프트 작성만" — 아래 템플릿으로 프롬프트만 작성하고 구현하지 않는다
- 설명, 질문, 커밋·푸시, PRD·상세기획

## 모드 순서

1. **Ask — 분석.** 읽기만 한다. 파일을 만들거나 고치지 않는다. 대상 파일, 현재 동작, 원인, 관련 계약을 확인하고 작업 프롬프트의 분석 절(먼저 읽을 것, 현재 상태)만 작성한다. 분석이 끝나면 Plan 모드로 전환을 요청한다.
2. **Plan — 계획.** Ask 분석을 바탕으로 작업 프롬프트 전체를 계획으로 작성한다. 복잡한 코드 제거 및 금지 조항을 포함한다. 사용자 확인 전에는 구현하지 않는다. 해석이 갈리면 계획 안에 가정으로 적지 말고 확인 질문으로 남긴다.
3. **Agent — 구현.** 사용자가 확인한 계획(작업 프롬프트)에 적힌 파일·동작만 수정한다. 계획이 없으면 구현하지 않고 Plan 모드로 되돌린다. 프롬프트에 없는 정리·개선은 하지 않는다.

모드 전환은 요청할 수 있는 범위만 쓴다. Plan과 Agent는 전환을 요청할 수 있다. Ask로는 전환할 수 없다. 사용자가 Ask에 있을 때 분석하고 Plan 전환을 요청한다. Agent에서 구현 요청이 바로 들어와도 확인된 계획이 없으면 코드를 고치지 않고 Plan으로 전환한다.

## 진행

1. 현재 모드를 확인한다. Ask면 분석만, Plan이면 계획만, Agent면 확인된 계획이 있을 때만 구현한다.
2. 대상 파일과 현재 동작을 읽는다. 현재 상태는 읽은 사실만 적는다.
3. Plan에서 아래 템플릿으로 작업 프롬프트를 계획에 작성하고 사용자 확인을 받는다.
4. Agent에서는 확인된 프롬프트 범위만 구현하고, 완료 확인 항목과 맞는지 본다.

## 작업 프롬프트 템플릿

Plan에서 계획을 쓸 때 이 구성을 따른다. "복잡한 코드 제거 및 금지" 절은 매번 아래 고정 조항을 그대로 넣는다.

```markdown
# <작업 이름>

## 목표
<한 단락. 사용자가 얻게 되는 동작>

## 먼저 읽을 것
1. `README.md` 목적 절
2. `.cursor/skills/apply-guidelines/SKILL.md` (가이드라인 저장소는 워킹 트리 밖에서 읽기만)
3. <대상 파일 경로>
4. <계약·화면안이 있으면 경로. 없으면 이 항목을 빼지 말고 "없음"이라고 적는다>

## 현재 상태
- <파일 경로>: <지금 동작. 읽은 사실만>

## 바꿀 것
1. <구체적인 요구사항>

## 유지할 것
- <바꾸면 안 되는 동작·파일·호출 흐름>

## 이번 작업에서 만들지 않음
- <범위 밖 항목>

## 복잡한 코드 제거 및 금지
- 한 화면·한 동작을 위해 새 추상 계층, 전략, 팩토리, 제네릭 헬퍼를 만들지 않는다.
- 같은 역할의 위젯, ViewModel, UseCase, 화면 흐름이 있으면 그것을 쓴다.
- 이번 변경으로 쓰이지 않게 된 분기, 플래그, 래퍼, 죽은 코드는 제거한다.
- 조건 중첩과 모드 플래그 조합으로 경우를 늘리지 않는다.
- 호출을 한 겹 감싸기 위한 파일은 만들지 않는다. 파일 분리는 책임이 분명할 때만 한다.
- 새 상태관리, 새 디자인 시스템, 카드 UI를 도입하지 않는다.
- 프롬프트 범위 밖의 리팩터, 이름 정리, 스타일 통일을 끼워 넣지 않는다.

## 완료 확인
- <확인할 동작>
```
