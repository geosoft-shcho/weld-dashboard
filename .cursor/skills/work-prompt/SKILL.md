# 구현·수정 작업 프롬프트

구현·수정은 Ask 분석, Plan 계획, 마크다운 저장, Agent 구현, 검증·검수 순서로만 진행한다. 단계를 건너뛰지 않는다. 확인된 계획과 그 프롬프트 마크다운이 없으면 제품 코드를 고치지 않는다.

`README.md` 목적과 `.cursor/skills/apply-guidelines/SKILL.md`는 기존 규칙대로 구현 전에 따른다. 이 스킬은 그 절차를 대체하지 않는다. 도구 중립 요약은 루트 `AGENTS.md`를 본다.

## 적용

적용:

- 화면, 위젯, 기능, 버그, 연동, 리팩터를 만들거나 고치라는 요청
- 구현해줘, 수정해줘, 추가해줘, 고쳐줘처럼 코드 변경이 목적인 요청

적용하지 않음:

- "프롬프트만", "프롬프트 작성만" — 아래 템플릿으로 마크다운만 작성하고 구현하지 않는다
- 설명, 질문, 커밋·푸시, PRD·상세기획

## 모드 순서

1. **Ask — 분석.** 읽기만 한다. 파일을 만들거나 고치지 않는다. 대상 파일, 현재 동작, 원인, 관련 계약을 확인하고 작업 프롬프트의 분석 절(먼저 읽을 것, 현재 상태)만 작성한다. 분석이 끝나면 Plan 모드로 전환을 요청한다.
2. **Plan — 계획.** Ask 분석을 바탕으로 작업 프롬프트 전체를 계획으로 작성한다. 복잡한 코드 제거 및 금지 조항과 완료 확인 기본 항목을 포함한다. 사용자 확인 전에는 구현하지 않고 프롬프트 파일도 만들지 않는다. 해석이 갈리면 계획 안에 가정으로 적지 말고 확인 질문으로 남긴다.
3. **마크다운 저장.** 사용자가 계획을 확인하면, 제품 코드를 고치기 전에 확인된 프롬프트를 `docs/<YYYY-MM-DD>/<작업이름>_프롬프트.md`에 그대로 저장한다. Plan은 파일을 쓸 수 없으므로 이 저장은 Agent에서 한다.
4. **Agent — 구현.** 저장한 마크다운만 읽고, 그 문서에 적힌 파일·동작만 수정한다. 문서가 없으면 구현하지 않고 Plan으로 되돌린다. 문서에 없는 정리·개선은 하지 않는다.
5. **검증·검수.** 구현 직후 `./scripts/agent_check.sh`(관련 테스트가 있으면 경로 인자 포함)를 실행한다. 아래 「구현 후 검수」를 통과하기 전에는 완료로 치지 않는다. 해당하면 회고를 남긴다.

모드 전환은 요청할 수 있는 범위만 쓴다. Plan과 Agent는 전환을 요청할 수 있다. Ask로는 전환할 수 없다. 사용자가 Ask에 있을 때 분석하고 Plan 전환을 요청한다. Agent에서 구현 요청이 바로 들어와도 확인된 계획이 없으면 코드를 고치지 않고 Plan으로 전환한다.

## 진행

1. 현재 모드를 확인한다. Ask면 분석만, Plan이면 계획만 한다.
2. 대상 파일과 현재 동작을 읽는다. 현재 상태는 읽은 사실만 적는다.
3. Plan에서 아래 템플릿으로 작업 프롬프트를 계획에 작성하고 사용자 확인을 받는다.
4. 확인 후 Agent에서 그 프롬프트를 `docs/<YYYY-MM-DD>/<작업이름>_프롬프트.md`로 저장한다. 날짜는 확인한 날이다. 파일 이름은 공백 없이 작업 내용을 드러낸다.
5. 구현은 그 파일만 따른다. 채팅의 계획과 파일이 다르면 파일을 따른다.
6. `./scripts/agent_check.sh`를 실행한다. 관련 테스트 경로가 프롬프트에 있으면 인자로 넘긴다. 실패하면 고친 뒤 다시 돌린다.
7. 「구현 후 검수」항목을 확인한다. 완료 확인의 UX·동작 항목과 맞는지 본다.
8. 오판·거절한 diff·반복 실수가 있으면 「회고」를 남기고, 반복이면 rule/스킬 금지 조항으로 승격한다.

"프롬프트만 작성"이면 4번에서 멈추고 5번 이후를 하지 않는다.

## 구현 후 검수

Agent가 사용자 검수 전에 확인한다.

- 「바꿀 것」 밖 파일이 바뀌지 않았다.
- 「복잡한 코드 제거 및 금지」를 어기지 않았다.
- import·API·proto 필드가 실제 코드/계약과 일치한다.
- `./scripts/agent_check.sh`가 실패하지 않았다. 실패면 완료로 치지 않는다.
- 범위가 부족하면 프롬프트 문서를 고친 뒤 재구현한다. 프롬프트만 반복해서 우회하지 않는다.

## 회고 (선택)

오판, 거절한 diff, rules/스킬에 올릴 반복 실수가 있을 때만 쓴다.

- 프롬프트 말미에 짧게 적거나 `docs/<YYYY-MM-DD>/회고_<작업>.md`로 남긴다.
- 같은 실수가 반복되면 `.cursor/rules` 또는 해당 스킬의 금지·완료 확인에 올려 다음 작업부터 막는다.

## 작업 프롬프트 템플릿

Plan과 마크다운 파일이 같은 구성을 쓴다. "복잡한 코드 제거 및 금지" 절은 매번 아래 고정 조항을 그대로 넣는다. "완료 확인"의 기본 세 줄은 매번 유지하고, 작업별 항목은 그 아래에 추가한다.

```markdown
# <작업 이름>

## 목표
<한 단락. 사용자가 얻게 되는 동작>

## 먼저 읽을 것
1. `README.md` 목적 절
2. `.cursor/skills/apply-guidelines/SKILL.md` (가이드라인 저장소는 워킹 트리 밖에서 읽기만)
3. <대상 파일 경로>
4. <계약·화면안이 있으면 경로. 없으면 이 항목을 빼지 말고 "없음"이라고 적는다>

## 현재 상태
- <파일 경로>: <지금 동작. 읽은 사실만>

## 바꿀 것
1. <구체적인 요구사항>

## 유지할 것
- <바꾸면 안 되는 동작·파일·호출 흐름>

## 이번 작업에서 만들지 않음
- <범위 밖 항목>

## 복잡한 코드 제거 및 금지
- 한 화면·한 동작을 위해 새 추상 계층, 전략, 팩토리, 제네릭 헬퍼를 만들지 않는다.
- 같은 역할의 위젯, ViewModel, UseCase, 화면 흐름이 있으면 그것을 쓴다.
- 이번 변경으로 쓰이지 않게 된 분기, 플래그, 래퍼, 죽은 코드는 제거한다.
- 조건 중첩과 모드 플래그 조합으로 경우를 늘리지 않는다.
- 호출을 한 겹 감싸기 위한 파일은 만들지 않는다. 파일 분리는 책임이 분명할 때만 한다.
- 새 상태관리, 새 디자인 시스템, 카드 UI를 도입하지 않는다.
- 프롬프트 범위 밖의 리팩터, 이름 정리, 스타일 통일을 끼워 넣지 않는다.

## 완료 확인
- `./scripts/agent_check.sh` 통과 (`dart analyze`)
- 관련 테스트가 있으면 `./scripts/agent_check.sh <test 경로…>` 통과
- <확인할 UX·동작>
```
